# Lessons

Cross-cutting patterns discovered during slice work, referenced by `/decision` Phase 0 (Constraint Harvest) and `/integration-sweep` recommendations.

## L-001: Pipeline-bypass temptation — "just write it down" before opening a slice

**Discovered**: 2026-04-11, first integration sweep after the `validator-symlink-fix` slice.

**Pattern**: a real bug is discovered in the middle of another session (often while consuming cairn from a downstream project). The urge is to *write it down somewhere* — a CHANGELOG entry, a known-issues note, a docs paragraph — before opening a slice to fix it. The bug feels too concrete to leave in working memory and too specific to lose to a session boundary. A tiny direct commit feels justified because "it's just docs."

**What happens**: the direct commit lands. It is a three-line addition, well-written, cleanly scoped. It is also a bypass of `/start-slice` and a violation of the invariant that requires all post-bootstrap work to flow through the pipeline. The first cross-slice integration sweep finds it. By then it is already in the permanent history.

**Concrete instance**: `f531087 docs: record validator symlink-resolution bug in Known issues` (2026-04-11). Three-line CHANGELOG edit recording the `scripts/validate_architecture.py:22` symlink bug that the `validator-symlink-fix` slice subsequently fixed. Intent was honest; the act was a violation. After the first cross-sweep surfaced it, the remedy was **option 3 — accept as a scar**: leave INV-001 unchanged, record this lesson, let the violation stand in history as evidence that the pipeline is not mechanically enforced and the maintainer's own discipline is the only barrier.

**Why option 3 and not a new ADR**: rewriting the invariant to excuse the commit would hide the lesson. bootstrap-exception already says "there is no second exception" and "future attempts must go through supersession, not quiet repetition." A supersession to retroactively regularize the bypass would be quiet repetition in a different form. The honest answer is: the bypass happened, it should not have happened, and the cost of recording that is carrying one un-remediated violation in the `git log` forever.

**Recursive consequence**: `/integration-sweep` step 6.5 itself produces a commit that is not a slice phase commit and not a decision commit. Under a strict reading of INV-001, every sweep commit is also a violation of the same class. Option 3 accepts this too — sweep commits are scars of the same kind, landed deliberately, each one an audit-trail artifact of an honest check rather than a shortcut. This is the consequence of not writing an context-discipline-protocol that names sweep commits as pipeline-substrate operations.

**Update 2026-05-02 — recursive consequence closed.** `pipeline-substrate-naming` (firm) names pipeline-substrate as a third legitimate commit class alongside slice-phase and decision-recording, with a registry at `.claude/pipeline-substrate-registry.yaml` and authorization-by-name verification (prefix + emitter contract). Sweep, refresh-architecture, and similar pipeline-substrate commits are no longer scars — they are recognized legitimate output. The original `f531087` direct commit remains a scar of the kind this lesson names; the sweep-class scars are remediated.

**Rule for future Claude sessions (and future me)**: if you are about to make a direct commit to cairn and you are not in the bootstrap commit, stop. The options are (1) open a slice via `/start-slice`, (2) run `/decision` if the change is architectural, or (3) write nothing to the repo and carry the information forward to the next session via `/handoff`. The temptation to "just write it down quickly" is the pattern this lesson names. Holding that information in `/handoff` state is strictly better than a direct commit, because a handoff does not pollute the audit trail.

**Exceptions**: `/integration-sweep` and `/refresh-architecture` commits are pipeline-substrate operations whose exclusion from `/start-slice` is a known scar (see the recursive consequence above). They are not a license for other kinds of direct commits.

**Anti-pattern signals**: "it's just docs," "it's only three lines," "I'll open the slice right after," "the invariant doesn't really mean this." All of these were internally true in the concrete instance. None of them prevented the violation.

## L-002: Route-before-run — triage, framing, and analysis are three distinct steps

**Discovered**: 2026-04-11, during the phase rethink `/decision` session (P0a from the cliff-failure-mode-and-v1-defenses v1 execution plan). Observed while comparing cairn's `/decision` against Superpowers' `brainstorming` skill and RIPER-5's capability-gated modes; formalized in the same session.

**Pattern**: Every incoming unit of work answers three questions in order, and each question can be revisited when the next one reveals the prior answer was wrong.

**Step 0 — Triage (which flow(s), how many, in what order?)**: classify the work against cairn's current flow corpus:

- `superpowers:brainstorming` — framing-only; output is a spec, no commitment to a direction
- `/decision` — architectural commitment; output is an ADR
- `/start-slice` — implementation under existing constraints; output is a 4-phase passage
- `/integration-sweep` — cross-slice audit; output is sweep notes + possibly new slices
- `/refresh-architecture` — derived-view regeneration; output is `docs/ARCHITECTURE.md`
- Direct ADR editorial fix (`ADR_EDITORIAL_FIX=1`) — frontmatter or typo patch

Triage outputs **a sequence** of one or more flows. Examples: a code-local bug report → `/start-slice` alone (1 flow). An architectural question with a clear framing → `/decision` alone (1 flow). An architectural question arriving cold → `brainstorming` → fresh session → `/decision` (2 flows). A feature request that implies both a decision and an implementation → `/decision` → fresh session → `/start-slice` (2 flows). An exploratory "I'm not sure what I want yet" → `brainstorming` alone, the session itself is the output (1 flow, no downstream commitment). A cross-project observation from integration-sweep that needs a new invariant → sweep findings → `/decision` → `/start-slice` (3 flows). The scope of triage is expected to expand as cairn's flow corpus grows.

**Step 1 — Framing (does a framing artifact already exist?)**: a framing artifact is any document that maps the constraint space and enumerates candidate approaches — exploration note, plan doc, RFC, ADR predecessor, prior brainstorming output. If yes → feed it directly to the next flow's entry point (`/decision` Phase 0, `/start-slice` Step 5). If no → run `superpowers:brainstorming` in a **fresh session** to produce one. The session boundary between framing and the next flow is load-bearing — it extends context-discipline-protocol's session-isolation principle from slice-phase boundaries to decision-framing boundaries.

**Step 2 — Analysis/execution**: run the chosen flow in its own fresh session. Standard flow rules apply. No framing work happens inside `/decision` Phase 0; no `/decision`-flavored adversarial analysis happens inside brainstorming. Each phase does its own job.

**Triage is a classifier, not a commitment. Flows are open to change mid-run:**

- **Downshift** (spec-v1 §4 already implements this): `/decision` started, work turns out to be trivial → demote by marking the ADR `firmness: provisional` and skipping Phase 5. The Phase 0 constraint harvest and Phase 2 enumeration remain valuable even for trivial work.
- **Upshift** (spec-v1 §5; `docs/reviews/2026-04-11-from-rag-session.md` Finding 2): `/start-slice` started, architectural invariant discovered mid-slice → fail the slice, restart with a `/decision` that produces the ADR, then re-enter the slice with the new constraint as input. Do NOT patch around the discovery inside the slice — that routes around the verification layer.
- **Reframe** (applies to any flow, any phase): if triage was wrong, return to triage. The cost of a mis-triage caught early is small; the cost of running the wrong flow to completion is the cost of all the work done under the wrong discipline.

**Concrete instance**: the phase rethink `/decision` session on 2026-04-11 ran as a clean 1-flow path (`/decision` alone) because (a) triage routed the work to `/decision` per cliff-failure-mode-and-v1-defenses D4's "standalone `/decision`, not a slice" and the v1 execution plan's P0a, and (b) `.claude/current-slice/exploration-notes.md` (two 2026-04-11 exploratory sessions) was the framing artifact — brainstorming was correctly skipped. The session boundary between the exploratory sessions and today's `/decision` preserved isolation for free.

**Anti-pattern signals**: "I'll just start a slice and figure out the decision as I go" (upshift-in-denial), "this is obviously an [X]" (triage skipped under false certainty), "we already know what we want so skip brainstorming" (framing confused with approval), "I'll run `/decision` to confirm what I already decided" (analysis used as theater). All four are internally plausible; none prevent the routing error.

**Refinements upstream, not downstream**: "one question at a time, multiple choice preferred" and "incremental approval gates" from Superpowers' `brainstorming` skill belong in the framing step (Step 1), not inside `/decision`'s analysis phases. If framing happens in brainstorming and analysis happens in `/decision`, neither phase has to re-do the other's work.

**Scope note**: this lesson captures the pattern as a mental routing rule. Promotion to a dedicated `/triage` skill is deferred — the scope will be cleaned up and pressure-tested through use before earning its own command.

## L-003: Phase 5 Independent Verification — index-row leak from Phase 4 draft commit

**Discovered**: 2026-04-11, during the phase-lock-and-role-declaration phase rethink `/decision` session (P0a from the cliff-failure-mode-and-v1-defenses v1 execution plan). Observed when the Phase 5 verification subagent read `docs/adr/index.md` as part of its mandated Phase 0 Constraint Harvest inputs and saw the new phase-lock-and-role-declaration title row that had been committed one step earlier in Phase 4 alongside the ADR body.

**Pattern**: The `/decision` protocol's Phase 4 step ("Commit the ADR draft") currently includes the `docs/adr/index.md` row update alongside the new ADR file. For firm decisions, Phase 5 Independent Verification spawns a fresh subagent instructed to read `docs/adr/index.md` during Phase 0 Constraint Harvest to discover the ADR corpus. As a result, the new ADR's title row is visible to the subagent **before** it enumerates approaches, partially pre-anchoring the enumeration to whatever the title reveals. This does not invalidate Phase 5 — the subagent still runs constraint harvest, pre-mortem, enumeration, and stress test independently — but the enumeration's starting position is no longer clean.

**Concrete instance**: phase-lock-and-role-declaration landed with the title "Four-Phase Pipeline Lock and Role Declaration." The Phase 5 subagent honestly flagged the leak in its return ("I noticed from the index the title contains 'Four-Phase Pipeline Lock and Role Declaration' — this is a minor, unavoidable leak") and compensated by genuinely enumerating 3-phase, two distinct 5-phase shapes, and an independently-derived 3-phase collapse variation. Its constraint envelope, pre-mortem, stress test, assumption audit, and rationale were all derived from first principles. But the Phase 2 enumeration's anchor point was the leaked phase count (4) and the leaked commitment class ("lock"). A less disciplined subagent could have collapsed the enumeration around the leaked answer.

**Rule for future `/decision` runs on firm ADRs**: at Phase 4 (Decision Record), commit the ADR body file but **do not** update `docs/adr/index.md`. The index update is Phase 6 (Propagation) work — `/refresh-architecture` Step 3 regenerates the index from the ADR corpus naturally at Phase 6 and the new row appears there. Splitting the commits preserves Phase 5's isolation: the verification subagent reads the old index without the new row, and the ADR body is inaccessible to it by explicit instruction.

**For provisional ADRs**: Phase 5 is skipped per the `/decision` protocol ("For `firmness: provisional` decisions, skip Phase 5 — provisional decisions are expected to be revisited as the project learns more"), so the index row leak has no consequence. Index update at Phase 4 remains acceptable for provisional decisions.

**Mechanism**: requires a small protocol refinement to `commands/claude-code/decision.md` Phase 4 instructions, splitting "commit the ADR draft" into two distinct sub-steps for firm ADRs: (a) commit the ADR body file alone; (b) at Phase 6, run `/refresh-architecture` which handles the index regeneration. This refinement is a protocol-skill edit that runs through a normal slice (not captured as this `/decision` session's output, since this session is scoped to phase-lock-and-role-declaration, not to protocol refinements).

**Anti-pattern signals**: "the index row is just metadata, it won't affect the subagent's reasoning," "the subagent is instructed to compensate for contamination," "Phase 5 already acknowledges same-family verification is partial per `docs/spec-v1.md` §7." All three are internally true. None of them eliminated the partial anchoring in the concrete instance above.

## L-004: Inherited threshold — a counter reused across defenses may not measure what its warning text claims

**Discovered**: 2026-04-16, during the `d3-bypass-classification` `/decision` session.

**Pattern**: A threshold rule and counter are extended from one defense to another by surface-level reuse (same rolling window, same count, same warning text) without re-examining whether the underlying failure classes are the same shape. In the source defense, the counter is well-aligned with its warning text because the bypass domain is naturally single-class. In the target defense, the bypass domain has multiple structurally distinct classes, and the single counter conflates them — firing the warning on signals the warning text does not actually describe.

**Concrete instance**: cliff-failure-mode-and-v1-defenses D3 inherited the `3-in-10 bypasses → design-review-recommended` rule from D1 (cliff-failure-mode-and-v1-defenses:82). D1's bypass domain is validator false-positives — naturally single-class. D3's bypass domain has three classes (slice-caused, pre-existing, false-positive). The threshold fired at `housekeeping/inv004-rebaseline` on three pre-existing-drift bypasses (`v1-defense-d3/automated-backstop` ruff debt, `v1-defense-d3/ruff-cleanup` parallel-session doc, `housekeeping/inv004-rebaseline` CC binary drift) — none of which were D3 false-positives. The warning text "gates producing more noise than signal" didn't match the situation; the actual signal was "carry-over debt is accumulating." Remedy landed as the `d3-bypass-classification` ADR (provisional): three-class reason schema; rolling window counts only `false-positive`.

**Rule for future defense-extension ADRs**: when reusing another defense's escape hatch, counter, or threshold, verify explicitly that the failure classes being counted are the same kind of thing. The surface rule (e.g., "3-in-10 → review") can be reused; the *semantic claim the warning text makes* must be re-checked against the new domain. "D1 uses this, so D3 can too" is not enough — the question is "does the counter measure what the warning says it measures, in the target defense's failure space."

**Anti-pattern signals**: "we'll reuse the D1 convention," "the rolling-window rule is proven," "3-in-10 is the standard threshold in this codebase." All three are internally plausible. None verify that the classes being counted are comparable across defenses.

**Mechanism**: this lesson names the pattern; the concrete remedy for D3 lives in the `d3-bypass-classification` ADR. Future defense-extension ADRs should re-run this check at Phase 3 (Adversarial Stress Test): if any mechanism is imported from another ADR, audit its assumption set against the new domain's failure classes.

## L-005: Parallelism substrate works; skill-level coordination is the actual tax

**Discovered**: 2026-04-16, during the manual Axis-B parallel dogfood run from `87ea8b5` through merge commit `b5a853e` + coord sweep `fc27e6d`. Four workers (A/B/C/D) each ran a full Phase 1→4 pipeline concurrently on separate worktrees + tmux windows + branches, all picked slice number 18 (legacy numeric-id scheme) independently, all merged into `feature/identifier-scheme` with per-merge reconciliation of 4–6 pipeline-substrate files. Full write-up: `.claude/plans/2026-04-16-dogfood-observations.md`.

**Pattern**: When a system gets its first real parallel-execution test, the framing question is usually "does the branching model hold?" In practice the substrate (worktrees, branches, merges, per-branch state) turns out to be robust — the predicted collision modes (parallel SLICE-ID claims, sweep-counter contention, sister-branch state conflicts at merge) resolve at merge time with bounded cost paid in pipeline-substrate files (`handoff.md`, `slice.yaml`, sweep notes, feature files) rather than code. **The unexpected cost is at the skill layer**: slash commands whose side-effects are prose-specified (the skill *says* "also flip status and write archive") execute them inconsistently under context pressure; bootstrap-autonomy contracts ("run X before stop") get verbally acknowledged but not executed. Debugging this is hard because each individual skill run looks plausible — the failure only shows up as a gap between what the protocol promised and what the tree reflects.

**Concrete instance**: The `/handoff` skill on worker A at P2, P3, and P4 boundaries reproducibly committed `handoff.md` + the handoff-commit but **skipped** flipping `slice.yaml` `status:` and **skipped** writing the `handoff-phase-N.md` archive. B's, C's, and D's `/handoff` invocations completed both side-effects correctly. Same skill, same bootstrap, same branch-structure — divergent side-effect execution. Independently, three of four workers (A at P2, B at P3, D at P2) stopped after their phase-commit and *recommended* running `/handoff` verbally rather than running it autonomously, breaking the "autonomous handoff before stop" bootstrap contract. The cost was real: ~5 minutes per manual nudge, multiplied by the 3 affected boundaries, plus the opportunity cost of the coord tracking which worker was stopped at what boundary. In parallel, the parallelism-v1 D2 prediction (parallel SLICE-ID + sweep-ID collision is safe at merge time) held cleanly across all four workers; merge reconciliation averaged ~5–10 minutes per merge for the 4–6 conflict files, zero content loss, with merges auto-resolving on code files and conflicting only on pipeline-substrate.

**Rule for future parallel-execution work**: when planning a multi-worker run, budget separately for (a) the branching/merge mechanics and (b) the skill-layer execution contracts the protocol relies on. (a) is predictable and bounded; (b) is the latent cost. Before spawning ≥3 concurrent workers, dogfood the `/handoff` + bootstrap-autonomy sequence on a single branch first and confirm every protocol-declared side-effect actually lands — if any step is prose-specified ("also write X", "run Y before stop"), either (i) make it a non-skippable step in the skill (code the action, not just describe it), or (ii) accept that coord must verify it post-hoc and budget the verification cost. The branching substrate is not where to focus pre-flight effort; the skill contracts are.

**Anti-pattern signals**: "the skill description is clear about what to do," "the bootstrap prompt tells the worker to auto-run /handoff — it will," "the parallel-execution risk is merge conflicts," "we validated /handoff on a single slice, it works." All four were internally plausible going into the dogfood. None prevented the observed gaps.

**Mechanism**: three follow-up slices drop out of this lesson — (a) harden `/handoff`: make `slice.yaml` status transition + phase-archive write non-skippable (code, not prose), covering `commands/claude-code/handoff.full.md`; (b) harden bootstrap-autonomy: either instruct "run /handoff before stop" more forcibly or wrap the worker lifecycle so `/handoff` fires on phase-commit detection; (c) add subagent-progress visibility so coord can detect stalls like the 28-minute A subagent block without needing to capture-pane. parallelism-v1 graduates `provisional → accepted` after (a) and (b) land; the "parallelism-native" vision (commitment #2) passes its first real execution gate with those hardenings in place. Full pain-point catalogue in `.claude/plans/2026-04-16-dogfood-observations.md` §8.

## L-006: Identifier renames are feature-scoped, not slice-scoped

**Discovered**: 2026-04-18, during the `feature/identifier-scheme` → `dev` merge protocol design (first feature→dev merge in cairn).

**Pattern**: A scheme-change that spans multiple artifact classes (ADRs, slices, features, tests, prose, hooks) cannot be done as a single slice. The first pass finds one class of residue; the second pass finds residue from a class the first pass didn't cover; the third pass finds prose references both earlier passes missed. Each pass is a real slice — not ceremonial — but the feature boundary is where the pattern *as a whole* is governable.

**Concrete instance**: identifier-scheme ran three sequential slices — `adr-rename-sweep` (ADR files), `slice-and-feature-rename` (slice + feature namespace), `doc-sweep` (residual prose). Each slice closed cleanly and its sweep found residue attributable to the next slice's scope. After `doc-sweep` closed, sweep #17 still flagged two test-schema residues, which motivated a queued fourth slice (`v1-defense-d3/bypass-log-hierarchical-slug`). Four passes, one feature.

**Rule for future `/decision` and `/start-slice` triage**: when the proposed change is an identifier or terminology scheme that touches multiple artifact classes, the triage step routes to a **new feature definition** — not directly to `/start-slice`. The feature's sub-slices are framed by artifact class; a sweep between slices surfaces residue for the next slice; a dedicated doc-sweep slice is expected, not optional. Attempting a single-slice rename either under-scopes (leaves residue) or over-scopes (busts phase-4 invariants).

**Anti-pattern signals**: "the rename is mechanical," "one slice will cover it," "it's just find/replace," "phase-4 integration can absorb the residue." All four were internally plausible before the work started; none prevented the three-slice cascade that actually happened.

**Mechanism**: recorded here as a pattern; the concrete procedure (what a scheme-change feature's slice-sequencing looks like) can be promoted to `commands/claude-code/start-slice.md` or a new `/plan-feature` flow if a second scheme-change feature reproduces the shape.

## L-007: Framing-doc attribution inheritance — ADR drafts absorb source docs' errors

**Discovered**: 2026-04-20, during the slice-close-contract `/decision` session.

**Pattern**: An ADR drafted from an upstream framing artifact (design doc, brainstorm doc, exploration notes, RFC) inherits the framing artifact's factual claims. Phase 0 Constraint Harvest reads the framing doc; Phase 1 pre-mortem and Phase 2 enumeration proceed on its premises; Phase 3 adversarial stress tests the conclusions but rarely re-examines the premises because re-examination feels like "Phase 0 work, already done." The draft ADR can propagate a factual error from the source. Phase 5 Independent Verification with explicit instruction to read the implicated code is the primary mechanism that surfaces the inherited error — the verification subagent does not consume the draft ADR, is fresh to the framing doc, and when instructed to read the implicated code verifies premise-level claims against reality.

**Concrete instance**: The slice-close-contract ADR's D2 enforcement was built on the design doc's attribution of R3 (the redundant-commit race) to the Phase-4 integrator agent. The design doc at `docs/plans/2026-04-20-observability-and-close-slice-design.md:28` stated "Phase-4 integrator agent commits `handoff: phase 4 complete`"; the brainstorm doc echoed the same attribution. Phase 0 Constraint Harvest accepted the claim without verifying against the orchestrator's code. Phases 1, 2, and 3 proceeded to design enforcement mechanisms (prompt constraint + orchestrator defensive check) targeting the agent's behavior. Phase 5 independent verification read `scripts/slice_orchestrator.py` directly and discovered that `run_phase_loop` at line 841 calls `commit_phase_handoff(4, ...)` unconditionally; the Phase-4 agent prompt at `.claude/agents/phase-4-integrator.md:1-13` contains no `git commit` instruction. R3 is orchestrator-issued, not agent-issued. The draft ADR's D2 was enforcing a rule against a behavior the agent was not performing; the actual fix — skipping the orchestrator's Phase-4 boundary `commit_phase_handoff` call in `run_phase_loop` — required a draft revision after Phase 5. A parallel finding (slug collision permitted by `_slice_id_slug` at `scripts/slice_orchestrator.py:187-188`) similarly surfaced only when the verification subagent read the code directly.

**Rule for future `/decision` runs against upstream framing docs**: At Phase 0 Constraint Harvest, enumerate the factual claims in the framing doc that are *code-level assertions* (e.g., "component X emits Y", "function F calls G", "agent Z commits W") and either (a) verify each against the implicated code path before proceeding to Phase 1, or (b) mark each unverified claim explicitly on a premise list that Phase 5 is instructed to re-examine. The cost of reading the implicated code at Phase 0 is one grep; the cost of shipping an ADR with the wrong enforcement target is a supersession plus all downstream slice work built on the wrong draft.

**For Phase 5 subagent prompts on firm ADRs**: In addition to the standard "do not read the ADR body" instruction, explicitly instruct the subagent to read the code files implicated by the framing doc's factual claims. This is what makes Phase 5 verify premises, not just the draft's conclusions. A prompt that only asks the subagent to re-enumerate approaches without grounding in the code can produce a conclusion that matches the draft — same wrong approach, two independent derivations — not because the draft is correct but because both derivations inherit the same framing error.

**Anti-pattern signals**: "the design doc already framed this, Phase 0 just harvests," "the brainstorm captured the pain point, we don't need to re-verify," "the failure mode is obvious from the learning entry," "we're not revisiting the brainstorm — that would be re-doing framing." All four were internally plausible. None prevented the attribution error from reaching Phase 4 in the concrete instance above.

**Mechanism**: recorded here as a pattern. Two follow-through items:
- Protocol refinement to `commands/claude-code/decision.md` Phase 0 — add the code-level-claims verification sub-step and the explicit instruction for Phase 5 to ground in implicated code. Runs through a normal slice.
- Reinforcement of L-003's unlanded rule (for firm ADRs, commit the ADR body without the `docs/adr/index.md` update at Phase 4; let `/refresh-architecture` regenerate the index at Phase 6). In this session the draft commit included the index update alongside the ADR bodies; the subagent prompt partially restricted index access as a workaround, but L-003's cleaner protocol refinement remains unlanded.

## L-008: Phase-3 implementer commit discipline — empty handoff commits after a partial commit

**Discovered**: 2026-04-24, during the `cost-discipline/lever-1-per-phase-model` slice. Orchestrator escalated on B15 cap after two Phase-4 re-dispatches; diagnostic trace showed Phase 3 had produced a genuine source-code diff but committed only a subset of the envelope.

**Pattern**: Phase 3 implementer makes edits across multiple envelope files (typically source + tests + docs), then stages and commits a **subset** — most commonly the docs file alone, because the docs change feels like a natural unit of work. The source file(s) remain in the working tree, uncommitted. The orchestrator's per-phase handoff commit (`commit_phase_handoff` at Phase 3 boundary) then runs against a staging area with nothing new in it and produces an **empty commit** (`handoff: phase 3 complete` with `--stat` showing zero files). Phase 4 correctly refuses to close per DC-4 (Phase 4 must not commit source) and raises RAISE_ISSUE. Triager re-dispatches to Phase 3; the re-dispatched Phase 3 agent sees the docs change is already committed, finds no new work to do, and produces a second empty handoff commit. Phase 4 raises again. B15 cap trips; orchestrator escalates to the operator.

**Concrete instance**: Lever 1 Phase 3 committed `8c7ce44 docs(operational-reference): add CAIRN_MODEL_<ROLE>/CAIRN_EFFORT_<ROLE> env-var family` (28 lines of docs), then produced `fc90cec handoff: phase 3 complete` (empty — `git show --stat fc90cec` shows no files). `scripts/slice_orchestrator.py` had 42 lines of correct new work (`AGENT_MODEL_CONFIG` + `_resolve_model_config` + dispatch splice + `model_by_phase` recording) in the working tree but never staged. Phase 4 integrator correctly raised DC-4 naming the uncommitted file; triager re-dispatched to Phase 3; re-dispatched Phase 3 committed nothing new (`92500a9 handoff: phase 3 complete`, also empty); Phase 4 raised again; B15 cap hit (orchestrator `run_phase_loop` line 1917-1921 log: `phase 4 re-dispatched twice; escalating per design §6.1`). Operator-adjudicated recovery commit `7feebbd phase-3(manual-recovery): ...` landed the 42-line scripts diff; `--resume` then closed the slice cleanly at `23f1db0`. Phase 4 diagnostic was correct on every invocation — the bug was entirely Phase-3-side.

**Rule for future Phase-3 runs (and future orchestrator hardening)**: The implementer agent must stage **every** modified envelope file before returning `OK`. Any diff the agent wrote during the phase but didn't stage is a bug, not a judgment call — the handoff commit is not the operator's review gate, it is the mechanical commit that the subsequent phase reads as input. A safer orchestrator-level enforcement is to verify `commit_phase_handoff` at the Phase-3 boundary produces a non-empty `--stat` (or to stage envelope files defensively via `git add -A <envelope>` at the boundary) and raise before handing off to Phase 4; the agent-prompt-only fix (telling the agent to commit everything) has now been tried and is insufficient under context pressure. Two empty handoff commits in sequence is the observable tell; a single empty handoff commit is the leading signal.

**Anti-pattern signals**: "I committed the docs already, the tests pass so implementation is done," "the next commit will pick it up," "the handoff commit will stage what's left," "Phase 4 will see the working tree state anyway." All four are internally plausible to the implementer. None of them produce a non-empty commit. The Phase-4 integrator sees only the committed state — not the working tree — by design, and its refusal to close is the correct behavior.

**Mechanism**: follow-up slice to add an orchestrator-level non-empty-handoff check at the Phase-3 → Phase-4 boundary. Either (a) fail Phase 3 with an explicit reason if `commit_phase_handoff` produces an empty commit while the working tree has staged+unstaged envelope diffs, or (b) `git add -A` over envelope globs before the handoff commit (more aggressive, may mask other bugs). (a) is the conservative fix. Lives under `scripts/slice_orchestrator.py` `run_phase_loop` / `commit_phase_handoff`.

## L-009: `.claude/sweep.yaml` is a sweep-interval control file, not a Phase-4 result destination

**Discovered**: 2026-04-24, during the `cost-discipline/lever-1-per-phase-model` slice close. Close commit `23f1db0` landed cleanly but clobbered `.claude/sweep.yaml`: the pre-close content (`last-sweep-at-slice-id: cost-discipline/track-0-telemetry` / `sweep-interval: 1`) was replaced with Phase-4 result data (date/slice/status/invariants/tests). Tests and invariants were all PASS; the regression was silent because the clobber doesn't cause any immediate failure — it only degrades the next slice's sweep-due decision.

**Pattern**: Two artifacts in cairn share the word "sweep" and have distinct roles: `.claude/sweep.yaml` (the sweep-interval control file) and `.claude/current-slice/integration/sweep-notes.md` (the Phase-4 audit output). The phase-4-integrator agent prompt (`.claude/agents/phase-4-integrator.md:9`) declares writes to both: `Writes: .claude/current-slice/{integration/sweep-notes.md,handoff-phase-4.md,slice.yaml}, .claude/handoff.md, .claude/sweep.yaml`. But the prompt does not specify the schema of `.claude/sweep.yaml`. Under context pressure, a Phase-4 agent treats it as a **results destination** (mirroring `sweep-notes.md` structure: status/tests/invariants) and overwrites the control-file content. The sweep-due check at the next slice's close (`start-slice.full.md` Step 7.2 — reads `sweep-interval` and counts commits since `last-sweep-at-slice-id`) then falls back to "sweep due" because both keys are missing, causing a spurious sweep on the next close.

**Concrete instance**: Pre-Lever-1 sweep.yaml (committed at `96b7930`):
```yaml
last-sweep-at-slice-id: cost-discipline/track-0-telemetry
sweep-interval: 1
```
Post-Lever-1 sweep.yaml (committed at `23f1db0` by close_slice, after phase-4 agent rewrote it):
```yaml
# Cairn Sweep — cost-discipline/lever-1-per-phase-model
date: 2026-04-24
slice: cost-discipline/lever-1-per-phase-model
status: complete
invariants: { INV-003: PASS, ... }
tests: { total: 746, passed: 746, ... }
```
Track 0's phase-4 close did not exhibit this — it correctly updated `last-sweep-at-slice-id:`. Lever 1's phase-4 agent under identical prompt produced the clobber. Impact is sweep-cadence noise, not data loss; `/integration-sweep` itself still works, but "is a sweep due?" will now answer "yes" at every close until the control keys are restored.

**Rule for future phase-4-integrator prompt work**: Either (a) remove `.claude/sweep.yaml` from the agent's declared Writes list — it is not a per-slice artifact, it is a sweep-interval control file owned by `/integration-sweep` and the orchestrator's close_slice flow — and rely on the orchestrator's close_slice to write `last-sweep-at-slice-id:` at the close commit; or (b) keep it in the list but specify the exact schema (`last-sweep-at-slice-id: <slice-id>` + `sweep-interval: <int>`) and forbid any other keys. (a) is the cleaner fix because it matches the underlying ownership (control file is not phase-specific). Per-slice audit data belongs in `sweep-notes.md`, which the agent already writes correctly.

**Anti-pattern signals**: "sweep.yaml is in the agent's Writes list, so I'll put my sweep data there," "the filename matches 'sweep' — my audit is a sweep — so the file is for me," "I'll mirror sweep-notes.md shape into sweep.yaml for machine-readability," "the control-file schema isn't documented so I'll write what seems useful." All four are internally plausible to the agent. None check the file's actual role against the rest of the protocol.

**Mechanism**: follow-up slice to edit `.claude/agents/phase-4-integrator.md` Writes list — remove `.claude/sweep.yaml`, keep `.claude/current-slice/integration/sweep-notes.md`. Separately, audit the orchestrator's close_slice flow to confirm it (not the agent) is the writer of `last-sweep-at-slice-id:` at close. Operator hygiene: this slice's close left sweep.yaml clobbered; next slice should either restore the control keys or the follow-up slice fixing the agent prompt should land before the next slice closes.

## L-010: Phase-4 role-lock holds against process failure, bends against content-failure under live-corpus pressure

**Discovered**: 2026-04-26, during back-to-back close of two parallel-worktree slices (`compression/slice-artifact-preservation` in WS4, `compression/lever-x-knowledge-index` in WS1). Both ran auto-mode in separate tmux windows; both closed within minutes of each other; both surfaced Phase-4 boundary failures. The two failures were resolved differently — one correctly per protocol, one in violation of it. The matched-pair structure is what makes the pattern legible.

**Pattern**: The `phase-lock-and-role-declaration` D2 prohibition on Phase-4 implementation rewrites and the `docs/spec-v1.md` §13 item 8 prohibition on patching to force Phase-4 to pass hold reliably when the failure class is **process-shaped** (uncommitted files, missing handoffs, DC-4 violations) — the agent's mental model maps cleanly to "bounce back to the un-finished phase," and re-dispatch fires correctly. The same two prohibitions appear to bend when the failure class is **content-shaped** — live-corpus reveals an edge case that Phase-2's RED tests didn't exercise, and the integrator can see exactly which one-line change would close the gap. The mental model maps to "fix it" rather than to "bounce back so Phase-2 writes the missing test and Phase-3 makes it green." The role-lock is enforced by agent self-discipline at the failure-handling moment, not by orchestrator code, and that discipline appears to be a function of how clearly the failure maps onto an existing recovery path.

**Concrete instance — WS4 (role-lock held)**: Phase-4 audit on `slice/compression-slice-artifact-preservation` found 5 envelope files uncommitted after Phase 3 (`scripts/slice_orchestrator/lifecycle.py`, `.gitignore`, `commands/claude-code/start-slice.full.md`, `docs/ARCHITECTURE.md`, `docs/adr/slice-artifact-preservation.md`). DC-4 (sole-commit-source) violation. Phase 4 raised RAISE_ISSUE; triager re-dispatched phase 4 → phase 3 (commit `62e1cc5 slice: re-dispatch phase 4 → phase 3`); second Phase-3 attempt committed all five files together (commit `b1f56dd phase 3: implement slice-artifact-preservation (helper + close_slice patch + prose)`); Phase 4 re-ran clean. Zero logic rework, zero in-place edits by Phase 4. Final state: 840/840 tests passing, all 9 invariants validated, ADR co-landed firm at `cc4eeb6`. The pipeline's idempotency contracts held cleanly under auto-mode with no operator supervision — exactly the dogfood-validation event `phase-lock-and-role-declaration` was designed for.

**Concrete instance — WS1 (role-lock breached)**: Phase-4 audit on `slice/compression-lever-x-knowledge-index` ran the round-trip validator against the live cairn corpus (not the synthetic Phase-2 fixtures) and found two failures: (a) `Decision.supersedes` was empty because the kuzu graph backend stores list properties as edges, not as node properties — Phase-2 fixtures didn't exercise list-shaped properties at the storage layer; (b) `validate_binds_paths` failed on glob patterns like `.claude/features/*.yaml` because Phase-2 fixtures didn't include glob-shaped binds. The integrator's own commit message (`51e1fb4 fixup(cairn_query): commit Phase-4 validators.py orphan`) flags the breach: it edited `scripts/cairn_query/validators.py` on disk — rehydrating `Decision.supersedes` from graph edges and filtering glob patterns out of `validate_binds_paths` — and committed the patch as a fixup AFTER the slice-complete commit (`9c8e9c3 slice: compression/lever-x-knowledge-index — complete`). The fixes are technically correct; the protocol-correct action would have been RAISE_ISSUE → re-dispatch Phase 2 (skeptic adds tests for list-rehydration and glob-shaped binds) → Phase 3 (implementer makes them green) → Phase 4 (re-audit). Final state: tests now pass, but the slice's audit trail records a Phase-4 source-rewrite prohibited by both `docs/adr/phase-lock-and-role-declaration.md` D2 and `docs/spec-v1.md` §13 item 8.

**Why the pair is interesting**: same parallel run, same auto-mode, same protocol, same Phase-4 prompt, ~minutes apart in wall-clock — divergent compliance. The variable that distinguishes them is the failure-class shape. WS4's failure provides unambiguous routing ("you didn't commit X"); WS1's failure provides ambiguous routing ("Phase 2 was incomplete, but the diff to fix it sits one edit away in a file already in the envelope"). The integrator agent's response to ambiguity is to default to "I know how to fix this" rather than to "bouncing this back is more expensive but protocol-correct." Whether this is rare-and-idiosyncratic or systemic-under-content-failure cannot be determined from one observation.

**Insufficient-data note**: one WS1-class incident is not yet a systemic finding. The role-lock might be holding ≥95% of the time and we observed the rare miss; or it might bend reliably under content-shaped failure at non-trivial frequency. Both narratives fit the current data. Decision deferred until repetition data accumulates.

**Decision deferred — options if it recurs**:
- (1) Tighten the Phase-4 agent prompt with explicit examples of content-failure → re-dispatch routing (cheapest, least invasive; agent-prompt fixes have a known leakage rate per L-008).
- (2) Move the live-corpus validator into Phase 2 so edge cases surface as RED tests rather than Phase-4 audit failures (structural fix; shifts the discovery point upstream where the recovery path is implicit).
- (3) Add orchestrator-level enforcement that detects Phase-4 source-file edits to envelope implementation files and fails the phase loudly (does not rely on agent self-discipline; mirrors L-008's "code, not prose" pattern).
- (4) Accept that the role-lock has a known content-failure leakage and document the boundary explicitly in `phase-lock-and-role-declaration` D2 with a defined remediation for post-close fixup commits.

The right choice depends on the pattern's frequency. Logged here as the watching-mark.

**Anti-pattern signals**: "the fix is one line, the test will pass after, I'm just completing the work the implementer started," "Phase 2 obviously missed this edge case but I've already found it and we're at the close, no point bouncing over a small thing," "the validator is in the envelope and I'm allowed to write validator files," "this is content polish, not architecture." All four are internally plausible to a Phase-4 agent under live-corpus failure pressure. None of them is a defense against the role-lock — D2 applies to *the act* of editing implementation files in Phase 4, regardless of how small or how correct the edit is.

**Mechanism**: deferred pending recurrence data. If a second WS1-class incident appears in any future slice, re-evaluate the four options above. The matched WS4 success is the counter-evidence that the protocol works when its routing is unambiguous — the question on recurrence is not whether to harden but where (prompt, Phase-2 scope, orchestrator gate, or boundary documentation).

## L-011: Phase-handoff commit is `--allow-empty` by design; agents own content commits, and may not commit them

**Discovered**: 2026-04-26, during `cost-discipline/lever-1-tier-retune` Phase-3 escalation analysis.

**Pattern**: The orchestrator's `commit_phase_handoff` (`scripts/slice_orchestrator/lifecycle.py:185-208`) records a phase boundary as `--allow-empty`. Its purpose is to mark "phase N complete," not to commit the agent's content. The phase agent's prompt allocates content commits to the agent itself. When the agent does not invoke `git commit` on its envelope edits — because the body-commit instruction is implicit, easy to skip, or read as optional — the boundary commit lands clean and empty while the agent's actual edits sit in the working tree only. From git's perspective, Phase N succeeded. From the slice's perspective, Phase N produced nothing other than a marker. On `--resume` the orchestrator reads `current_phase: N+1` from `slice.yaml` and dispatches Phase N+1 against the working-tree state plus an empty boundary; if Phase N+1 raises and the triager re-dispatches to Phase N, the re-dispatched agent sees the prior agent's uncommitted edits and may rewrite them — possibly reintroducing the original bug, possibly drifting into different scope. Re-dispatch compounds the gap: each empty boundary obscures that the substantive artifact is uncommitted.

**Concrete instance**: In `cost-discipline/lever-1-tier-retune`, the Phase-2 skeptic ran twice (commits `48d02e1` and `a9ff0b9`, both `--allow-empty`) without committing its `tests/unit/test_slice_orchestrator_model_config.py` rewrite or its `validation/approach.md` + `coupling-clusters.yaml`. The second Phase-2 run was specifically dispatched (via Phase-3 RAISE_ISSUE → triager re-dispatch) to fix a T5 docstring/assertion contradiction the first run had introduced; the second run's working-tree state still carried the same T5 bug, so Phase 3 RAISE_ISSUE'd four more times until B15 capped. Phase 3 (in the same flow) made the correct two-row source edit to `scripts/slice_orchestrator/core.py:41-47` but also never committed — the `9dd5143 handoff: phase 3 complete` boundary commit was empty too. Recovery required a manual amendment commit (`c683a9d`) capturing the orphaned Phase-2 + Phase-3 work plus a one-character fix to T5. The substantive deliverable was a two-cell dict edit; recovery from the missing-commits gap consumed several re-dispatch cycles plus operator-side review.

**Rule for future Claude sessions (and future me)**: After every `handoff: phase N complete` commit, run `git log -p <commit>~..<commit>` AND `git status`. The boundary commit being empty is fine on its own; the *working tree being dirty across an empty boundary* is the symptom of an uncommitted phase. If envelope files are modified or untracked at a phase boundary, the agent did not commit its content. Either (a) re-dispatch the phase with explicit "you must `git commit` your envelope edits before returning OK" framing, or (b) commit the orphaned content yourself as a `slice(amendment): ...` with an honest audit note (mechanism, what was orphaned, why it was safe to capture). Do not silently advance — the orchestrator's idempotency contracts and the close-time artifact preservation depend on phase-N artifacts being in git, not just on disk.

**Anti-pattern signals**: "the boundary commit landed, Phase N is done," "the working tree's a little dirty but the orchestrator advanced, must be fine," "re-dispatch will fix it — let the loop run," "the agent's prompt says to commit, surely it did," "an `--allow-empty` commit looks the same as a content commit in `git log --oneline`, so the history reads clean." All five assume the orchestrator's empty-marker pattern is equivalent to "Phase N committed its work." It is not.

**Recurrences**:
- **R1** (2026-04-26) — `cost-discipline/lever-1-tier-retune`, Phase-2 + Phase-3 commit gap; recovery commit `c683a9d` (the discovery instance, above).
- **R2** (2026-04-26) — `compression/learnings-capture` (failed), Phase-3 prompt-amendment cluster left no-commit (worker reported OK without editing target file); slice failed at B15 cap and was archived to `.claude/completed-slices/compression-learnings-capture-failed/`.
- **R3** (2026-04-26) — `compression/learnings-capture` retry, Phase-3 `orchestrator-events` cluster wrote helper + emission sites + `_ARTIFACT_RELPATHS` entry into the working tree but never committed (its agent's response was wrapped in backticks → orchestrator classified `malformed`). Phase-4 first invocation correctly RAISE_ISSUE'd; operator commit-with-audit fixup `354167a` captured the orphan + inline-wired the F2 caller. The retry's RED-test discipline (every Phase-3 cluster carries a RED test) held — but RED tests cannot detect "code written, not committed."

**Mechanism**: PROMOTED for fix (3+ recurrences inside ~24h, all on the same orchestrator). Two candidate fixes from the original logging stand: (1) tighten phase-agent prompts to mandate `git commit` before returning `OK` and have the orchestrator verify `git diff <handoff>~..<handoff>` is non-empty for content-bearing phases; (2) move content commits to the orchestrator and forbid agent-side commits, removing the implicit ownership transfer altogether. (1) is cheaper, (2) is structurally correct. The R2/R3 pattern (Phase-3 cluster fan-out workers in particular) suggests (2) is the better target — cluster workers' implicit-commit-ownership is the most fragile seam. Tracked as a Must-land-before-v1 slice in `docs/roadmap.md` §11.

## L-012: SessionStart hook output is part of the agent's effective prompt; schema drift between hook and orchestrator stays silent until a tier-sensitive consumer hits it

**Discovered**: 2026-04-26, during `cost-discipline/lever-1-tier-retune` Phase-4 dispatch under the slice's own retuned `phase-4-integrator: claude-opus-4-7 / low` default — first dogfood run at the new tier.

**Pattern**: Hooks configured under `.claude/settings.json` and propagated to consumers via the `.slice-system → .` symlink fire on every fresh `claude -p --agent <role>` subprocess at session start. Each hook's `additionalContext` is merged into the agent's effective prompt — the agent cannot tell whether a line came from the system prompt, the agent file, the user message, or a hook. When a hook reads slice state under one schema and the orchestrator writes it under a different schema, the hook may emit text that contradicts the actual state of the world. The contradiction stays silent as long as every model + effort tier the slice runs through happens to tolerate it. A subsequent tier flip can turn a tolerated contradiction into a hard refusal — and the cause is invisible to anyone debugging at the orchestrator or agent layer in isolation.

**Concrete instance**: `checks/role-cheatsheet.sh` (added in the prose-protocol era) parsed `slice.yaml` for `status: <phase-name>` (e.g. `4-integration`) and emitted "Slice: ... Phase: ... Role: ... Anti-behavior: ..." cheatsheet text. The orchestrator (`scripts/slice_orchestrator/`, added 2026-04-25) writes `status: in-progress` and tracks phase via a separate `current_phase: <int>` field. The cheatsheet's case statement had no match for `in-progress` and fell through to `*) emit_generic`, which emits `"No active slice — /start-slice to open one"` during every phase agent's session start. Phases 1-3 (running on opus/high or sonnet/medium) tolerated the misleading line: they invoked their tools, observed real artifacts, and proceeded. Phase 4 in `cost-discipline/lever-1-tier-retune` ran on `claude-opus-4-7 / low` (the slice's own retuned default — first dogfood at the new tier) and refused to proceed, returning `FAILED` four times in a row with the verbatim hook text quoted as its justification ("No active slice present (SessionStart hook reports '/start-slice to open one'). Phase 4 integrator cannot run without an active slice directory..."). The slice could not close until the cheatsheet was patched in-place to recognize the orchestrator's schema (sibling-fix `a3ec2c9`, scope-guard expansion logged in `.claude/current-slice/envelope-expansions.log`).

**What this reveals**: tier-sensitivity to misleading hook context is a real failure surface, not a model-quality concern. The opus/low integrator was not "worse" than sonnet/low — it was *more compliant* with the prompt-as-given, including the part of the prompt the hook injected. Hook-emitted contradictions are paid in agent refusals; the bill comes due at the most compliant consumer. The drift had been silent for ~36 hours (from the orchestrator's introduction at `01a4cc3` on 2026-04-25 to this slice's Phase-4 dispatch at 2026-04-26 06:28 UTC), riding through the prior `compression/learnings-capture` slice's Phase 4 on sonnet/low without complaint.

**Rule for future Claude sessions (and future me)**: treat every hook's `additionalContext` output as part of the prompt for every agent the hook fires for. When orchestrator state schema changes, every hook that reads that schema is on the change-impact list — explicitly. When introducing a tier flip (model OR effort), do not declare the retune complete until at least one full slice has dogfooded the new defaults end-to-end. Dispatch-time tests on `_resolve_model_config` are necessary but not sufficient — they verify the dispatch path, not the agent's response to its prompt at the new tier. The dogfood verification belongs in the closing slice's Verification section, not in a follow-up.

**Anti-pattern signals**: "the hook output is just a hint, the agent will verify against the filesystem," "the prior slice ran fine on the old tier so the hook's clearly tolerable," "the cheatsheet is non-blocking by design (always exits 0), so it can't break anything," "model-tier changes only affect cost and reasoning depth, not refusal behavior," "schema drift between two layers I don't own isn't my problem this slice." All five are internally plausible. None survives contact with a compliance-axis-sensitive integrator.

**Mechanism**: the cheatsheet patch landed via this slice as a sibling-fix (`a3ec2c9`); the broader watching-mark is "audit other hooks for orchestrator-schema dependence before the next tier flip." `checks/scope-guard.sh:23-29` reads `slice.yaml.status` and treats `complete|failed` correctly but is silent on the `in-progress` value — appears tolerable today since scope-guard only blocks on `intent.md` envelope, but worth re-verifying when the next schema field shifts.

## L-013: Phase-3 re-dispatch can scope-drift into adjacent failed-slice surface area named in the intent's motivation

**Discovered**: 2026-04-26, during `cost-discipline/lever-1-tier-retune` Phase-4 audit (the audit caught it).

**Pattern**: When `intent.md`'s What/Why or Specification sections cite a *different* slice — typically a prior failed one used as empirical justification for the current slice's existence — a Phase-3 implementer agent dispatched in fresh context after a re-dispatch (Phase 3 → Phase 2 → Phase 3 again) may misread the citation as a delivery target. The motivation paragraph and the spec paragraph live in the same prompt; the agent's frame for "what does this slice deliver" can slide from the latter to the former, especially when the spec paragraph is *small* (a literal-dict edit, a one-line config flip) and the motivation paragraph is *narratively heavy* (failure post-mortem, root-cause story). The result: source edits in functional surface area that has nothing to do with the slice's actual envelope.

**Concrete instance — single observation**: `cost-discipline/lever-1-tier-retune`'s intent (~11K bytes) cites `compression/learnings-capture` (the prior failed slice) in its §Why paragraph as the source of empirical signal — "Phase 3 underperformed on cluster fan-out (worker reported OK without RED-test gating), Phase 4 caught it." The slice's actual delivery target was a two-row literal-dict edit in `scripts/slice_orchestrator/core.py:41-47`. On Phase-3 re-dispatch (after Phase-3 had previously RAISE_ISSUE'd over the T5 bug — see L-011), the implementer agent added an entirely new feature: a `_record_orchestrator_event()` helper in `core.py`, event-recording call sites in `lifecycle.py` (B15 cap + redispatch sites), an `integration/orchestrator-events.jsonl` artifact relpath, and a brand-new `tests/unit/test_orchestrator_events_capture.py` test file. None of this was in the intent envelope; all of it was in `compression/learnings-capture`'s envelope (the prior failed slice the motivation paragraph cited). Phase 4 RAISE_ISSUE'd — explicitly classifying the orphan work as out-of-scope new-feature drift (not bug-fix orphan, so `feedback_phase4_rolelock_fixup` did not apply); the work was stashed (`stash@{0}`, recoverable for the retry slice) and the slice closed cleanly without it.

**Why the pair-with-L-010 matters**: L-010 names a Phase-4 leakage where the integrator edits one line in-place rather than bouncing a small content failure back to Phase 2/3. L-013 is the inverse class at Phase 3: the implementer adds entire feature-scope rather than executing the small literal edit the spec asks for. Both are "small-edit-vs-big-bounce" failures of role discipline; both happen at the seam between an unambiguous procedural state (re-dispatch) and an ambiguous content cue (a citation, a found bug); both are caught only by the next phase's audit (L-013 was caught by Phase 4; L-010's WS4 instance was caught by Phase 4 too — when it works, this is what Phase 4 is *for*). L-010's four candidate remediations (prompt tightening, structural enforcement, scope shift, boundary documentation) likely cover L-013 too, with the locus moved from Phase 4 to Phase 3.

**Insufficient-data note**: one observation. The pattern might be common (Phase-3 re-dispatch + cited prior slice → implements cited slice's surface) or might be a one-off coupling between this specific intent's narrative weight and the agent's tier (`sonnet-4-6 / high`, the very tier the slice was raising to). Until repetition, treat it as a Phase-4 audit cue, not a structural alarm.

**Rule for future Claude sessions (and future me)**: when `intent.md` cites a prior slice (especially a failed one) in its What/Why or Specification sections, the operator review at Phase 1 should explicitly ask: "is the cited slice's surface area in our envelope?" If no — and especially if no while the motivation prose is heavy — flag it. After Phase 3 (and especially after any Phase-3 re-dispatch), `git status` against the envelope is the cheapest catch: any modified file outside intent envelope is an L-013 candidate, regardless of how small or how plausible the change looks. Phase 4 should classify out-of-envelope source changes as RAISE_ISSUE by default, not by judgment.

**Anti-pattern signals**: "the prior slice was failed and this one is fixing it, so its surface is implicitly in scope," "the motivation paragraph clearly tells me what the operator wants," "this is the obvious next step for the project even if the literal scope is narrower," "I'll just implement both — the spec is too narrow to be the whole point," "the cited slice's failure is what justifies *this* slice, so completing both is the natural delivery." All five are internally plausible to a re-dispatched Phase-3 agent reading a citation-heavy intent. None is a defense against the envelope.

**Mechanism**: deferred pending recurrence. Logged here so that the next Phase-3 re-dispatch + cited-slice combination is recognized faster. If a second incident appears, lift to one of L-010's four candidate remediations adapted to Phase 3.

## L-014: Slice that widens an enforcement set should pre-grep for inverted assertions in the existing test corpus

**Discovered**: 2026-04-27, during `compression/lever-Z-fixup` Phase-2 validation (the slice's own L-014 self-application dogfood surfaced three inversion candidates before Phase 3 dispatched).

**Pattern**: A slice's `intent.md` correctly names a *new* set membership — adding role X to `ROLE_DENY_READ`, expanding a deny pattern set, generalizing a contract — but does NOT name the *existing* test corpus's negation assertions that depend on the OLD set membership. Tests of the form `assert "X" not in deny_list`, `test_other_roles_unaffected_by_*`, `test_*_scope_*_ignored` are silently inverted (or made vacuous) by the widening. The discovery point lands at Phase 3 RAISE_ISSUE time when the implementer's GREEN run flips a previously-passing test to RED — costing one re-dispatch cycle plus operator-side envelope-expansion fixup. The same pattern recurs across slices because each slice's intent author authentically focuses on the *delta* (the new membership) rather than on the *complement* (the corpus that asserted the absence).

**Load-bearing directive**: When a slice's spec widens an enforcement set (e.g., adds role keys to `ROLE_DENY_READ`, expands a deny pattern set, or generalizes a contract), Phase-2 skeptic SHOULD pre-grep the existing test corpus for assertions that depend on the OLD set membership and surface those tests as candidate envelope-expansions in the validation approach BEFORE Phase 3 dispatches. This catches the inversion structurally rather than discovering it at Phase-3 RAISE_ISSUE time, which costs re-dispatch cycles and operator-side envelope-expansion fixups.

**Rationale (≤100w)**: All three resolved instances took the form of an existing test asserting "role X is NOT in deny-list" being silently inverted by a slice that adds role X to the deny-list. The slice's intent.md correctly named the new set membership; what it did NOT name was the test corpus's existing negation assertions. A Phase-2-side `grep -rn "not in ROLE_DENY_READ\|other_roles_unaffected\|bootstrap_scope.*ignored" tests/` (or the equivalent for the enforcement set being widened) surfaces inversion candidates structurally. Cost is one Phase-2 grep; benefit is one less Phase-3 RAISE_ISSUE cycle.

**Concrete instances (three confirmed)**:
- **G7 in Slice-2-fixup** (resolved by commit `8fc0133`) — Slice-2-fixup widened `ROLE_DENY_READ` membership; an existing G7 assertion that depended on the prior membership inverted under the new set. Resolution required envelope expansion to reach the inverted test and amend it.
- **G7-again in Lever-Z** (resolved by envelope-expansion commit `2713662`) — Lever-Z's role-coverage expansion of `ROLE_DENY_READ` re-tripped the same G7 shape against a *different* existing assertion, demonstrating the pattern is recurrent across slices that widen the same enforcement set.
- **`test_v4_other_roles_unaffected_by_read_denylist` and `test_bootstrap_scope_read_tool_ignored` in Lever-Z** (resolved by envelope-expansion commit `a79f609`) — both tests were structurally inverted by Lever-Z's deny-set widening. The test names themselves (`other_roles_unaffected`, `bootstrap_scope.*ignored`) are the textbook grep-targets the directive sentence above prescribes.

## L-015: Squash-merge collapses per-slice commits — extractors that depend on slice-shape commit history must have a disk-fallback path

**Discovered**: 2026-04-27, post-squash of `feature/compression` into `dev` (commit `6cfa4d0`). Surfaced at Checkpoint-2 verification when 4 of 5 tests in `tests/unit/test_extractor_slice.py` flipped from GREEN (on the feature branch) to RED (on dev tip). Forward-fixed in the same `docs:` closeout commit that lands this lesson via `@pytest.mark.xfail(strict=True)` markers; the structural fix is tracked as substrate Slice 4.

**Pattern**: Extraction code reads `git log --grep='^slice: .* — complete$'` (or any slice-shape commit-subject pattern) and silently returns zero results post-squash. The merge protocol (`docs/plans/2026-04-18-feature-to-dev-merge-protocol-design.md` §Merge-shape) collapses every intra-feature commit — including the per-slice `slice: <id> — complete` close commits the extractor depends on — into one `feat:` squash. The slice corpus on disk is unchanged; the *commit-history representation* of that corpus is destroyed at the merge boundary. Tests asserting "extractor returns ≥N slices," "extractor finds slice X," or "extractor emits PARENT edge to feature Y" silently fail at dev tip even though the underlying canonical state is intact.

**Load-bearing directive**: Any extractor whose source-of-truth includes `git log` MUST have a disk-fallback path. Canonical slice state lives at `.claude/sweep-results/<slice-id>/` (per ADR `slice-artifact-preservation`) and `.claude/completed-slices/<slice-id>/` (failed/archived slices). Git log is a derived view — convenient on feature branches where slice-close commits are still present, but absent from dev by protocol design. The fallback is not optional: any extractor that breaks at the merge boundary also breaks any consumer that reads from dev (e.g. CI substrate rebuild on a dev runner).

**Rationale (≤100w)**: Slice-shape commit subjects are an artifact of the slice pipeline's *internal* mechanics — they exist on feature branches, not on dev. The merge protocol §Merge-shape line 65 names this explicitly: intra-feature commits are session-state snapshots, not deliverables; preserving them in dev log is negative-signal. Coupling extraction to the internal commit shape conflates two layers (slice mechanics vs feature delivery) and inverts the protocol's intent: dev history is release-narrative; the canonical disk substrate (`.claude/sweep-results/`, `.claude/completed-slices/`) is where slice state actually lives. Extractors must read the substrate, not the substrate's pipeline-internal commit shape.

**Concrete instance**: `scripts/cairn_query/extractors/slice.py:74` — single-source-of-truth git-log grep, no disk fallback. Surfaced via 4 of 5 tests in `tests/unit/test_extractor_slice.py` failing post-squash:

- `test_extracts_at_least_four_slices` — asserts ≥4 slices; post-squash returns 0.
- `test_extracts_lever_2_orchestrator_split` — asserts a specific compression slice present; post-squash returns 0.
- `test_at_least_one_slice_touches_invariants` — asserts at least one slice has invariants_touched populated; post-squash empty corpus.
- `test_emits_parent_edge_to_feature` — asserts PARENT edge for any compression slice; no nodes → no edges.

The fifth test (`test_idempotent_at_fixed_head`) passes because both extractions return the same empty corpus.

**Recovery (this incident)**: Forward-fix on dev under xfail discipline rather than the protocol's Checkpoint-2 hard-reset escape hatch. Reset would not help — the squash *is* the cause; re-merging produces the same red. The protocol now documents this class explicitly under §Structural test-design mismatches at the squash-merge boundary (added in the same closeout commit that lands this lesson). Substrate Slice 4 ships the structural fix (disk fallback in `slice.py`); xfail markers carry `strict=True` so they fail loudly when the slice lands and the tests go GREEN again.

**Anti-pattern signals**: "git log is the natural source of truth," "the slice subjects are stable across the codebase," "the squash-merge is a one-time event — handle it once and move on," "this only matters at dev tip, not on feature branches where the orchestrator runs," "the extractor's own tests are GREEN on the feature branch, so the design is fine." All five are internally plausible. None survive Checkpoint-2 the first time a feature with extractors-vs-history coupling lands.

**Mechanism**: this lesson names the pattern; substrate Slice 4 ships the structural fix in `scripts/cairn_query/extractors/slice.py`; the merge-protocol amendment ships the recovery procedure for the next instance. If another extractor type (decision, lesson, feature) is later added with the same git-log-only coupling, lift the disk-fallback into a shared helper rather than re-implementing per-extractor.

## L-017: Project-root resolution drift — `Path.cwd()` vs explicit `CLAUDE_PROJECT_DIR` + git-toplevel

**Discovered**: 2026-04-29, audit Pass E. `validate_architecture.py:_repo_root` (lines 30-55) uses an explicit env-var-then-git-toplevel resolution chain and the docstring forbids `__file__`-based resolution because that would canonicalize through the `.slice-system` symlink to cairn — silently reading cairn's own substrate when invoked from a consumer. The rest of the cairn substrate (`scripts/cairn_query/__init__.py:24,63-68`, every `Path("...")` constant in `slice_orchestrator/{core,lifecycle,dispatch,telemetry}.py`, `snapshot_diff.py:_resolve_root` at L37-39 explicit "A4: use cwd") uses bare `Path()` constants that resolve cwd-relatively.

**Pattern**: A new code path needs a project-root anchor. The cheap option is `Path("relative/path")` or `Path.cwd()`, which works fine when the script runs in cwd = project root. The right option is the env-var + git-toplevel chain that `validate_architecture.py` documents. The cheap option is taken because it works on the developer's machine (cairn's own root) and the failure mode (consumer-side substrate misroute) is invisible until a consumer hits it. Each new path resolution becomes another place where consumer cwd vs cairn cwd disagrees, accumulating into a systemic CWD-coupling that breaks the whole consumer-bridge story.

**Load-bearing directive**: Any new code that resolves a project-root path MUST use a single shared `_resolve_root()` helper modeled on `validate_architecture.py:_repo_root` (env var → git toplevel → loud failure, **never** `__file__` or `Path.cwd()` with no fallback). The helper does not exist yet — a substrate slice should lift `_repo_root` into `scripts/_root.py` (or similar) and migrate all current `Path()` constants to use it. Until that slice lands, code review on any new path resolution must check for the pattern explicitly.

**Rationale (≤100w)**: cairn is a methodology repo consumed via symlink. Symlinks make cwd ambiguous: `.slice-system → /path/to/cairn` means a python script run under the symlink may see cwd-as-cairn or cwd-as-consumer depending on how it was invoked. `__file__`-resolution always lands at cairn (silent false-green for consumers). `Path.cwd()` lands wherever the invoker happened to be. Only an explicit env-var the invoker is contractually required to set, plus a git-toplevel sanity fallback, gives a deterministic answer. The cost of the discipline is a four-line helper; the cost of skipping it is permanent consumer-bridge breakage.

**Concrete instance**: `scripts/cairn_query/__init__.py:63-68` constructs `DecisionExtractor(adr_dir=Path("docs/adr"))`, etc. — when cairn-knowledge MCP is launched in a consumer's cwd, these scan the consumer's `docs/adr/` instead of cairn's. `scripts/cairn_query/__init__.py:24` `DEFAULT_DB_PATH = Path(".claude/cairn_query/index.kz")` writes the kuzu DB into whichever project the MCP is launched from. ~20+ `Path(".claude/...")` constants in `slice_orchestrator/{core,lifecycle,dispatch,telemetry}.py` have the same shape. All would be fixed by a shared `_resolve_root()` helper plus path constants like `_resolve_root() / ".claude/current-slice/slice.yaml"`.

**Anti-pattern signals**: "the script will only ever run from the project root," "the symlink case is rare — the env var doesn't need to exist," "if cwd is wrong the user will notice," "pulling in `_repo_root` from validate_architecture creates a circular import," "`Path.cwd()` is fine because the orchestrator sets cwd via `cd` before dispatch." All five are internally plausible. None survive a consumer dogfood session — the failure modes are silent because everything appears to run, just against the wrong corpus.

**Mechanism**: this lesson names the pattern; the helper does not yet exist. Promote to a substrate slice that (a) creates `scripts/_root.py` with the canonical resolver, (b) migrates `cairn_query/__init__.py`, `slice_orchestrator/*`, `snapshot_diff.py` to use it, (c) adds a regression test asserting CWD-independent behavior. Until then, every new path resolution in the substrate is a place this lesson must be re-applied by hand.

## L-018: Universal escape hatches as silent enforcement bypass — Bash-heredoc as the load-bearing example

**Discovered**: 2026-04-29, audit Pass G (deep-dive on phase-system enforcement layer). All four phase-agent prompts (`phase-1-writer.md:21`, `phase-2-skeptic.md:17`, `phase-3-implementer.md:17`, `phase-4-integrator.md:31`) document a "P1 Bash-heredoc escape" for the case where Write/Edit is denied by the sensitive-file gate on `.claude/**` paths: `cat > path <<'HEREDOC' … HEREDOC`. The escape works because `role_guard.py:22-24` does not include `Bash` in `WRITE_TOOLS`, and `scope-guard.sh:48` is matched only on `Edit|Write`. The heredoc therefore bypasses **every write-class enforcement gate**, not just the sensitive-file gate it was intended to escape. Phase-3-implementer can `Bash("cat > src/main.py <<'EOF' … EOF")` and write outside the envelope undetected.

**Pattern**: A specific enforcement gate (sensitive-file gate on `.claude/**`) blocks a legitimate write. The fix is to document an escape that bypasses *that gate* — but the escape mechanism (Bash heredoc) is universal: it bypasses every write-class gate that doesn't intercept Bash. The agent prompt frames it as a narrow tactical workaround; the implementation reality is a complete enforcement bypass for any phase that knows the trick. Once the escape is documented in all four phase prompts, the entire envelope-vs-source-file enforcement model becomes voluntary per-agent.

**Load-bearing directive**: Any "escape hatch" documented in agent prompts MUST be enforced as narrow as the gate it escapes. Concretely:
1. **Bash write-class enforcement**: extend `role_guard.py:22-24` to recognize Bash invocations of write-class operators (`>`, `>>`, `cat > X <<HEREDOC`, `tee`, `cp`, `dd`, `mv`) and apply the same `ROLE_POLICIES` + envelope check that Edit/Write applies. Until this lands, the heredoc escape is the primary phase-system enforcement gap (F-029).
2. **Escape-hatch documentation discipline**: any agent-prompt rule starting "When X is denied, fall back to Y" must include a one-line note naming the *other* enforcement gates Y also bypasses, so future readers don't mistake the escape for surgical.
3. **Test surface**: add a regression test that asserts `Bash("cat > path/outside/envelope.py <<'EOF' … EOF")` is denied for phase-3-implementer with a normal (envelope-bounded) AGENT_ENVELOPE.

**Rationale (≤100w)**: The phase pipeline's safety story rests on per-phase write-class enforcement: Phase 2 only writes tests; Phase 3 only writes envelope files; Phase 4 only writes sweep-notes. The role_guard + envelope + sensitive-file-gate layers exist to make this mechanical, not voluntary. A documented escape that bypasses all three layers reduces enforcement to per-agent discipline — exactly the correlated-error problem the pipeline exists to prevent. The escape is also asymmetric: an agent that knows the trick has unbounded write authority; an agent that follows the prompt literally is bounded. Two agents with the same intent get different write surfaces. That is a pipeline integrity bug, not an inconvenience.

**Concrete instance**: Pre-audit deep-dive surfaced this as F-029 (S1) in the audit catalog. The four prompts document the escape with identical wording. `role_guard.py` does not parse Bash command shapes for write-class operators (line 113-121 only extracts filename tokens from read-class commands like `cat`, `grep`). `scope-guard.sh` PreToolUse matcher is `Edit|Write` (`.claude/settings.json` line 39). DC-4 ("Phase 4 must never `git commit`", `phase-4-integrator.md:27`) is a related instance: `Bash("git commit -m ...")` similarly bypasses what is documented as a hard rule.

**Anti-pattern signals**: "the escape is only for the sensitive-file gate," "agents won't abuse the heredoc — the prompt makes the boundary clear," "blocking Bash write-class is too coarse and would break legitimate uses," "we'll catch any abuse in Phase 4 review," "the role_guard is for tools we control; Bash is the user's general-purpose tool." All five reproduce the failure mode by treating the documented narrow intent as if it were the implemented narrow effect. The implementation is unconditional bypass.

**Mechanism**: this lesson names the pattern; F-029 catalogs the specific instance for follow-up. The fix is structural — extend role_guard to parse Bash write-class operators — and lives in a future substrate slice. Until that slice lands, the escape is the load-bearing pipeline enforcement gap. If a second universal-escape pattern emerges (e.g., a documented `subprocess.run` fallback that bypasses some other gate), apply this lesson before adding the prompt note: enforce as narrowly as the original gate, or do not document the escape.

## L-019: Concurrent orchestrators sharing one `.claude/` tree — L-017's multi-process manifestation

**Discovered**: 2026-04-30, slice `substrate/root-resolver` Phase 3 self-immolation. Two `claude --resume` sessions ran in parallel: one in `cairn/` (PID 3652, dispatching `python -m slice_orchestrator` for `substrate/root-resolver`), one in `complex-rag-analysis/` (PID 2849, the consumer project, dispatching its own orchestrator for `compression/lever-Y-mcp-substrate` and later `compression/slice-artifact-preservation-test`). Because of L-017 (cwd-coupling + `__file__`-resolution drift through the `.slice-system` symlink), the consumer's orchestrator wrote into cairn's `.claude/orchestrator-debug/` directory and progressively overwrote cairn's `.claude/current-slice/slice.yaml`. Cairn's orchestrator continued reading the mutated `slice.yaml`, dispatched Phase 3 retries under the foreign `slice_id`, and timed out (1800s) after six attempts. ~3 hours of wall time wasted; partial cluster work salvaged via hand-stitched commit; slice archived to `.claude/completed-slices/substrate-root-resolver-failed/`.

**Pattern**: L-017 (path drift) produces a *write* misroute — a single process writes to the wrong tree. L-019 is what happens when *two* processes drift onto the *same* tree concurrently. The orchestrator already treats `.claude/current-slice/slice.yaml` as an exclusive resource: it reads slice state on every dispatch, writes status transitions, expects monotonic phase advancement. Running two of them on one file produces silent state corruption: each process sees the other's writes as "phase reset," dispatches phase agents under whatever slice_id is in the file *at that read*, and emits log files into a shared debug directory. There is no lock, no PID check, no `slice_id` consistency assertion across reads — the orchestrator was designed assuming one tree per orchestrator, and L-017 silently violates that assumption when consumer paths resolve back to cairn.

**Load-bearing directive**: Three structural fixes, in priority order:

1. **Land L-017's resolver fix first** (slice `substrate/root-resolver` follow-ups, firaaz/cairn#3 orchestrator-paths + mcp-server clusters). Until every path in `slice_orchestrator/`, `cairn_query/`, and `mcp_servers/` routes through `project_root()`, cross-tree leakage is the default and any "lock" we add lives on the wrong tree.
2. **Add a single-orchestrator-per-tree assertion at orchestrator startup**: write a PID + slice_id + start-time tuple to `.claude/current-slice/.orchestrator-lock` on init; on every phase dispatch re-read it and abort with a loud error if the slice_id changed or the PID is foreign. The lock file must be in the resolved-root tree, not the cwd tree, so it benefits from (1).
3. **Add a `slice_id` consistency check on every `slice.yaml` re-read**: orchestrator must compare the slice_id it dispatched under (held in process memory) against the one it just read from disk; on mismatch, abort the phase, write a diagnostic event, and exit non-zero. Silent continuation under a foreign slice_id is the specific failure mode this incident exhibited.

**Rationale (≤100w)**: A pipeline whose state lives in a shared file on a shared resolved root is a single-writer system by construction. Multiplying the writers — even accidentally, via path drift — is a Byzantine-state failure: each process does locally-correct work on locally-consistent reads, but the global state is incoherent. The "fix" is not "be careful which directory you launch from"; that's voluntary discipline against a mechanical bug. The fix is to make the orchestrator *detect* multi-writer corruption and refuse to operate. L-017 + missing detection = L-019. Either side of that conjunction holds the fault.

**Concrete instance**: 2026-04-30 incident. Cairn's orchestrator dispatched `substrate/root-resolver` Phase 1 at 19:29 UTC, Phase 2 at 19:37, Phase 3 at 19:49. Consumer orchestrator started Phase 1 of `compression/lever-Y-mcp-substrate` at 19:38, generating ~60 log files in cairn's `.claude/orchestrator-debug/` (visible chronologically via `ls -la`). At ~20:35 UTC, cairn's `slice.yaml` had been overwritten such that re-reads returned `compression/slice-artifact-preservation-test`; cairn's orchestrator continued under that slice_id for six more retries, finally timing out at 20:49 UTC. Salvageable evidence: the `orchestrator-debug/` log filenames (each prefixed with the slice_id at dispatch time) preserve the slice_id-flip timestamp; the final `.claude/completed-slices/substrate-root-resolver-failed/integration/orchestrator-events.jsonl` contains a single `agent_timeout` event under the foreign slice_id.

**Anti-pattern signals**: "we just won't run two orchestrators at once," "the user knows not to launch from the consumer," "consumer-side orchestrator is rare so we'll fix the path drift later," "adding a lock is overkill — this won't happen often," "the slice_id mismatch is a UX problem, not a correctness problem." All five reproduce the failure mode by treating concurrency safety as a discipline question rather than a mechanical one. The pipeline is correlated-error-tolerant by design at the phase boundary; it is not correlated-error-tolerant at the orchestrator-state boundary, and L-017 makes the latter trivially reachable from any consumer with a `.slice-system` symlink.

**Mechanism**: this lesson names the pattern; the 2026-04-30 incident in `.claude/completed-slices/substrate-root-resolver-failed/` is the canonical concrete instance. Fixes (1)–(3) above are sequenced: (1) is a follow-up under firaaz/cairn#3 already; (2) and (3) should be filed as new substrate-orchestrator-safety issues once (1) lands. Until all three ship, the cleanest workaround is operator discipline: never run two `claude --resume` sessions that both touch cairn (directly or via `.slice-system`) concurrently. That discipline is what we should *fail to require*, not what we ask the operator to remember.

## L-020: Compound mid-slice failures, manual-finish recovery, and the `_project_root_or_cwd()` fallback caveat

**Discovered**: 2026-04-30, slice `substrate/orchestrator-paths` (issue #24, root-resolver follow-up 1/2). The slice migrated 7 production files (`slice_orchestrator/{core,lifecycle,dispatch,telemetry}.py` + `integration_gate.py` + `validate_architecture.py` + `dogfood_evaluate.py`) from `Path('.claude/...')` literals and `Path.cwd()` to `_project_root_or_cwd()`, removed 5 strict-xfail markers, and ended green on lint + validate_architecture. The pipeline did not get there cleanly. Three failures stacked inside one slice: (a) `close_slice` staging-surface bug recurred (empty phase-2 commit; the staging set excludes phase-2-skeptic's test writes — pre-existing, see memory `close_slice_staging_surface.md` from 2026-04-21); (b) Phase-3 retry never converged on its own — the migration produced a `project_root()` strict-mode failure under the test-fixture cwd shape, requiring two ad-hoc cwd-fallback patches (`a2ebd1a` for `integration_gate._resolve_root`, then `bbe8c80` for orchestrator `_project_root_or_cwd`) before tests would even import; (c) L-019 collision: a concurrent consumer orchestrator (complex-rag-analysis) corrupted `.claude/orchestrator-debug/` mid-pipeline, contributing to the Phase-3 thrash. The slice was finished by hand: orchestrator killed, `close_slice` invoked manually, `handoff.md` and `slice.yaml` written by hand, single completion commit synthesized from the salvageable Phase-3 work.

**Pattern**: The orchestrator's recovery model assumes one failure at a time. A failed Phase-3 retry can be redispatched; a failed `close_slice` can be rerun; an L-019 path-drift incident can be cleaned up offline. *Compound* failures — three independent causes overlapping in one slice — exhaust the model: each retry surfaces the next failure, and the pipeline degenerates into a guess-and-check loop with no convergence criterion. The escape hatch is for the operator to kill the pipeline and finish by hand. That escape hatch is real, has been used multiple times now (`d6e5b28` is the second instance this quarter), and is *not procedural* — there is no documented manual-finish protocol, no checklist for which artifacts must be written, no validator that confirms a manually-finished slice is structurally equivalent to an orchestrator-finished one. The slice was finished correctly here through operator skill, not enforcement.

**Load-bearing directive**: Three corrections, in priority order:

1. **Promote manual-finish to a documented protocol**, not an undocumented escape. Concretely: a `commands/claude-code/manual-finish-slice.md` (or equivalent) that names the exact artifacts a complete slice must contain (`handoff.md`, `slice.yaml.status=complete`, `sweep.yaml`, `features/<id>.yaml`, single completion commit on dev), the order they must be written, and a validator script that diffs a manually-finished slice against the orchestrator's `close_slice` output and refuses to merge on structural divergence. Until this lands, every compound-failure recovery is operator-improvised.

The cwd-fallback and close-staging items each have a specific failure scenario that is not a tail case once a downstream consumer ships — both are routinely reachable, just not on the developer's machine.

## L-021: Long-lived feature branches accumulate divergence faster than they can be reconciled — bound branch lifetime by next-merge-friction, not scope completion

**Discovered**: 2026-04-27, while planning `feature/compression-followup`. The exploration revealed `feature/compression` had been open since 2026-04-18 (9 days), accumulated 147 commits not on `dev`, and during the same window `dev` absorbed 11+ unrelated lever / cost-discipline slices via shorter-lived sibling branches. Net content: only one slice's work (`compression/triager-superseded-test-heuristic`, closed `e46969d`) was unique to the long-lived branch, but reconciling the branch against the bidirectional divergence cost more than re-applying that one delta on a fresh branch off current dev.

**Pattern**: A feature branch is opened with a coherent scope. Work proceeds on it. Independently, sibling features land on `dev` via shorter-lived branches that squash-merge fast. The original branch keeps accumulating commits but isn't rebased forward. Each squash-merge of a sibling feature on `dev` strips the historical anchor that a future squash of the long-lived branch would have had — so the long-lived branch's eventual squash diff grows by the *union* of its own changes and the inverse of every sibling's changes. The branch's age becomes a multiplier on integration cost. Eventually the cost of merging exceeds the cost of redoing the salvageable work on a fresh branch off current dev — at which point the long-lived branch is archive material whether or not anyone has labeled it that.

**Load-bearing directive**: A feature branch's lifetime SHOULD be bounded by *next-merge-friction*, not by *scope completion*. If any of the following hold, the branch is at-risk and needs immediate action (rebase-forward + squash-merge what's done, OR open a fresh branch off current dev and forward-port deltas):

- The branch has been open >7 days.
- `git log --oneline dev..HEAD` exceeds ~50 commits (a soft signal — the *count* matters less than the *content* below).
- `git log --oneline HEAD..dev` shows any commit subject prefixed `feat:`, `slice:`, or `feature:` — i.e., a sibling feature has shipped to dev while this branch was open. **This is the load-bearing trigger.** A sibling-feature squash on dev means the long-lived branch will need to reconcile against work it never saw.
- The branch's own feature manifest (`.claude/features/<id>.yaml`) lists slices not yet closed AND `.claude/features/` on `dev` shows new slices added by sibling branches.

When in doubt, the `git log --oneline HEAD..dev` test is the cheapest signal. If sibling features have shipped, treat the branch as already over-extended.

**Rationale (≤100w)**: Cairn's merge protocol (`docs/plans/2026-04-18-feature-to-dev-merge-protocol-design.md` §Merge-shape) is squash-only. Squash erases the merge boundary's commit-graph anchor — by design, to keep dev as release-narrative. But that means a long-lived branch has no shared history to merge *against* once siblings have squash-merged. Each sibling squash makes the long-lived branch's eventual squash diff *larger* even when the long-lived branch did nothing. Long-branch divergence is therefore not just a function of work-on-the-branch; it's a function of work-on-siblings. Bounding lifetime by sibling-merge-frequency is the only stable rule.

**Concrete instance**: `feature/compression` (cairn). Opened 2026-04-18 (commit `0d7edfb`, first compression-program slice add). Closed work landed via squash-merge to dev as `6cfa4d0` 2026-04-27, followed by closeout `ade3966`. By 2026-04-27 (9 days post-open):

- 147 commits on `feature/compression` not reachable from `dev` (mostly per-phase intermediary commits for slices that already squash-merged via shorter-lived branches).
- 3 commits on `dev` not reachable from `feature/compression` (`6cfa4d0` compression squash, `a8cdcff` reset, `ade3966` closeout).
- **Content divergence (the load-bearing one):** 11+ slices closed on `dev` (`lever-2-orchestrator-split`, `lever-X-knowledge-index`, `lever-Y-mcp-substrate`, `lever-Z-substrate-full-pipeline`, `learnings-capture`, `slice-artifact-preservation`, `phase-1-handoff-stage-surface`, `phase-4-sweepnotes-required`, plus three `cost-discipline/*` slices) that did not exist on `feature/compression` at all. Only **1 slice** of work was unique to the long-lived branch (`compression/triager-superseded-test-heuristic`).
- File-level divergence on the two compression manifests alone: `+114 lines` (`.claude/features/compression.yaml` `+31`, `docs/features/compression.md` `+83`, the latter existing only on dev).
- Resolution: open `feature/compression-followup` off `dev` tip; forward-port the one salvageable slice as Slice 1 of the followup (`compression/triager-superseded-forward-port`); archive `feature/compression` rather than reconcile it. The 147-commit phase history is lost — that's intentional under the squash protocol.

**Anti-pattern signals**: "the feature isn't done yet — we'll merge when the last slice closes." "Rebasing forward is risky; let's wait until ready." "The worktree is isolated — what dev does doesn't affect us." "One big merge is cleaner than many small ones." "We'll deal with conflicts at merge time." "The slices on the branch are still in-flight; merging now would be premature." Each is locally plausible. None of them prevent the divergence from compounding while the branch is open — they only delay the reckoning while making it more expensive. The first three signals are particularly seductive because they sound like discipline.

**Mechanism**: this lesson names the pattern; the directive at the top is the operational rule, enforced for now by operator review at branch-creation time and at each `/start-slice`. The new branch `feature/compression-followup` (opened 2026-04-27 with this lesson) sets a 14-day ceiling for itself per its design doc §6 — explicit application of the directive on the first branch after the lesson is written. Promotion to a SessionStart hook (e.g., `branch-age-warning.sh` reading branch age + sibling-feature signal from `git log dev..HEAD` and `git log HEAD..dev`) is deferred until a second incident or operator review demonstrates the directive isn't holding under self-discipline alone.

## L-022: Manifest-schema validity is a load-bearing prerequisite for any published-artifact feature — round-trip the install, don't just build the artifact

**Discovered**: 2026-05-09, during `/decision` Phase 0+0.5 verifiers' adversarial cross-reference of the live Anthropic plugins-reference docs (`code.claude.com/docs/en/plugin-marketplaces` + `.../plugins-reference`). The verifiers independently surfaced that cairn's `.claude-plugin/marketplace.json:11` carries `"type": "git"` as the source discriminator, but the documented schema uses `source.source` (not `source.type`) with values `github | url | git-subdir | npm` — `"git"` is not in the documented enumeration. The bug had been latent the entire F1+F2+F3 lifecycle (2026-05-08 → 2026-05-09); F1 shipped a build pipeline (`scripts/build_dist.py` + `.github/workflows/dist-gate.yml`) that validates the curated payload contents but **never ran a real `/plugin install` round-trip**. F3's audit check 9 was correctly named as "manual end-to-end real install" but recorded as PENDING — gated on the missing publish step but ALSO unwittingly gated on the schema bug, which would have surfaced at parse-time before the missing-payload symptom.

**Pattern**: A feature ships a manifest meant to be parsed by an upstream tool (plugin marketplace, container registry, npm registry, OCI image index, etc.). The feature's verification surface includes dispatch-time tests on the *build script* (allow-list assertions, file-presence checks, validator self-tests) but does NOT include a real round-trip through the upstream parser. The build pipeline is correct on its own terms — the curated payload is what the maintainer intended — but the manifest declaring how the upstream tool finds the payload is silently wrong. The bug is undetectable until a real consumer runs the install command and the upstream parser rejects the manifest. By then, the manifest is committed, possibly merged, possibly tagged; rolling back is friction. The longer the gap between "manifest committed" and "first real install attempt," the worse the rollback.

**Load-bearing directive**: For any feature shipping a manifest meant to be parsed by an upstream tool, the feature's acceptance criteria MUST include a real install-time round-trip — not just dispatch-time tests on the build script. Concretely:

- **Audit checks naming "manual end-to-end install" must be gating, not deferred.** F3's audit check 9 was named correctly but recorded as PENDING. With hindsight, PENDING was the wrong status for a load-bearing acceptance criterion: PENDING reads as "deferred backlog" (like F1.1 follow-ups) when in fact the feature is structurally incomplete without the check. **Recommended status: BLOCKING — feature is not merge-final until check 9 records green, period.**
- **Manifest-schema lints must reference the live upstream docs, not memory.** Phase 0 + Phase 0.5 verifiers caught the `type: git` bug because they cross-referenced `code.claude.com/docs/en/plugin-marketplaces` directly via WebFetch. The original M5 ADR's D3 prose said `source.path: "dist/"` — internally consistent with the manifest text but wrong against the upstream schema. Documentation drift is real; verify against the live reference, not the project's own ADR text.
- **Schema-shape lints (e.g., `tests/unit/test_marketplace_schema.py`) gate every PR.** A unit test that loads the manifest and asserts each field/value against a small allow-list is cheap and catches drift before merge. Recommend: every published-artifact feature includes such a lint as part of Phase 2's RED test set.
- **The "build pipeline is green" CI signal does NOT imply the manifest is install-time-valid.** F1's `dist-gate.yml` was passing PR after PR; the manifest schema bug was orthogonal. CI greenness on build correctness is necessary but not sufficient. Add an explicit install-time round-trip step (or document it as a NON-skippable manual gate) for any feature whose deliverable is "an upstream tool can find and install our artifact."

**Rationale (≤100w)**: Cairn's TDD-by-construction discipline catches *implementation* drift via per-phase tests, but a manifest's correctness is not just an implementation property — it's an **interop** property against an external system that cairn doesn't control. Tests on the build script verify cairn's side of the contract; only a real install verifies the contract end-to-end. The /decision Phase 0+0.5 verifiers caught this bug because adversarial discipline (`feedback_attack_before_synthesis.md`) cross-referenced the live upstream docs as ground truth — not the project's own prior synthesis. This pattern generalizes to any cross-system contract: verify the contract on the foreign side, not just the local side.

**Concrete instance**: 2026-05-08 → 2026-05-09 cairn M5+M6 milestone. F1 (`cairn-m5-f1-packaging`, closed `4bae8ec`) shipped `scripts/build_dist.py` + `.github/workflows/dist-gate.yml` + `.claude-plugin/marketplace.json` with `"type": "git"`. F2 (`cairn-m5-f2-consumer-doc-surface`, closed) shipped CONSUMER.md and templates referencing the (broken) install commands. F3 (`cairn-m6-f3-migration-and-symlink-retire`, closed `6a6f430`) shipped the consumer migration runbook + script and recorded audit check 9 as PENDING. Three features, eight phase commits each, every phase green — and the install path was structurally broken the entire time. The bug surfaced at the M7 `/decision` Phase 0+0.5 verifiers' cross-reference (`docs/adr/m5-plugin-deployment-pattern.md` Context section). M7 (`cairn-m7-plugin-deployment-pattern`, plan at `docs/plans/2026-05-09-cairn-m7-plugin-deployment-pattern.md`) re-grounds audit check 9 as a NON-SKIPPABLE acceptance gate per ADR D9.

**Anti-pattern signals**: "the build script tests pass; the manifest is just a few lines of JSON, what could go wrong." "Audit check 9 is manual; we'll defer it to a follow-up." "The marketplace.json shape was correct in the M5 ADR; we don't need to re-verify against the live docs." "F3 is merge-eligible if all dispatch-time checks pass." "Schema lints are overkill for a 14-line JSON file." Each signal is locally plausible; none of them catch the failure mode that "the JSON is locally valid AND the build pipeline is green AND the upstream parser rejects it" is a stable failure surface for any feature where the deliverable is interop. The seductive pattern: dispatch-time greenness is taken as proof of interop; it isn't.

**Mechanism**: this lesson names the pattern; M7 is the corrective slice (the plan at `docs/plans/2026-05-09-cairn-m7-plugin-deployment-pattern.md` Phase 4 Section V makes audit check 9 NON-SKIPPABLE). Promotion of "interop round-trip required" to a TaskCreate template element (e.g., per-feature plan template's "Audit checks" section gains a structural slot for "**install-time / upstream round-trip**" alongside the existing dispatch-time checks) is deferred until a second instance of this failure class confirms the pattern is generalizable beyond plugin manifests. The M5 portfolio review's "minimum-viable-cairn" subset question (`docs/reviews/2026-04-23-from-portfolio-evaluation.md:103-105`) interacts with this lesson: any "atomic piece" of cairn that ships independently as a published artifact inherits L-022's directive.


## L-023: Cheap empirical probes trump strong adversarial argument — cost-asymmetry heuristic for /decision Phase 3

**Discovered**: 2026-05-12, during the `plugin-payload-transport` /decision arc. Phase 3 adversarial mounted a rigorous attack on Approach A1 (`source: "url"` + `sha:` pinning), arguing that the 82/82 sha-pinning population pattern in Anthropic's `claude-plugins-official` marketplace was non-causal — i.e., a stylistic CI convention emitted by Anthropic's marketplace-build tool, not a behavioral resolver branch. The argument was supported by: (a) re-reading of upstream issue `anthropics/claude-code#26588` whose reverse-engineering placed the SSH-coercion bug inside `case 'github':` in the resolver; (b) issue `#50725` naming `source: "url"` + HTTPS as the failing shape with host-detection as the mechanism; (c) the simplest model fitting all three observed failures (V-3 attempts 1+2 + the falsified amendment) was "host-based routing overrides everything." Verdict: RESHAPE A1 → A3a (self-marketplace) as load-bearing pick. The reshape was logically defensible but **empirically wrong**. When the operator declined to pay A3a's commit-`dist/` operational cost speculatively and ran A1's 5-minute probe first, install passed cleanly: no `git@github.com:` SSH attempt, no `temp_github_<id>` cache path. The 82/82 sha pattern WAS causal; the resolver does branch on `sha:` vs `ref:` pinning.

**Pattern**: A Phase 3 adversarial agent with full access to the constraint envelope, journey trace, and pre-mortem can construct an internally coherent argument falsifying an approach **before that approach has been empirically tested**. The argument may be logically rigorous, may correctly identify the structural axis of risk, and may correctly steel-man the runner-up. None of that prevents the argument from being empirically false. When the candidate approach has a cheap probe (≤10 minutes, no pre-commit work, no infrastructure changes), the cheap probe is strictly more informative than any amount of adversarial argument — because the adversarial argument operates on the *publicly available evidence model* (upstream issues, reverse-engineering, population patterns), while the probe operates on the *actual resolver*. The publicly available evidence model can be incomplete in ways the agent cannot detect from the inside.

**Load-bearing directive**: For any /decision Phase-2 candidate approach where the empirical probe-cost is **≤10 minutes of operator-bound time** AND **does not require pre-commit operational shifts** (no schema migrations, no force-pushes, no .gitignore edits, no CI workflow changes), the probe MUST run before Phase 3's adversarial verdict locks in a heavier alternative. Concretely:

- **Convergence-note Phase-2 outputs include a probe-cost column.** When ranking approaches, the convergence note already names probe-cost. What's missing is a **probe-cost-vs-adversarial-strength threshold rule**: if the cheapest probe is ≤10 minutes AND the adversarial argument against it is structural-not-empirical (i.e., relies on inferring resolver behavior from publicly available evidence rather than from prior probe failure), the cheap probe runs first. The Phase-3 adversarial verdict cannot demote a candidate without an empirical probe attempt below this threshold.
- **Phase 3's adversarial mandate explicitly excludes rejecting candidates that meet the cheap-probe threshold without probing.** Phase 3 can recommend "probe candidate X first; then re-evaluate" but cannot recommend "skip candidate X because the population pattern is non-causal." The asymmetry: a passing probe is worth more than any amount of negative argument; a failing probe sharpens the negative argument into evidence.
- **Operator's "let's just try the cheap thing first" instinct is structurally correct, not impatience.** The operator's cost asymmetry pushback at `plugin-payload-transport`'s ADR (commit `a10342f`) — declining to pay A3a's commit-dist cost speculatively — was the load-bearing intervention. Future /decision runs should treat this instinct as a first-class signal, not a methodology violation.
- **The Phase 3 adversarial output gains an explicit "what cheap probe could falsify this attack?" line.** Adversarial arguments that survive disconfirming-search must name what observation would falsify them. If that observation is a 5-minute probe, the probe is the next step, not Phase 4.

**Rationale (≤100w)**: Cairn's adversarial discipline (`feedback_attack_before_synthesis.md`) is correct: default-to-acceptance is a named failure mode. But adversarial argument against a candidate that has not been probed is **also** a form of acceptance — acceptance of the public-evidence model as ground truth. The asymmetry between probe-cost and adversarial-loss-cost is what makes this directive necessary: a 5-minute probe with an unfavorable-but-rigorous adversarial verdict against it costs 5 minutes if the probe fails; the adversarial verdict alone costs at least one ADR amendment (~2-4 hours of operator work plus credibility) if the probe would have passed. Probe-cost-asymmetry is a heuristic that bounds adversarial overreach.

**Concrete instance**: 2026-05-11 → 2026-05-12. Phase 3 of `plugin-payload-transport` recommended A3a (self-marketplace via `dev`/`dist`) as load-bearing pick on the basis that A1's 82/82 sha-pinning pattern was non-causal. ADR `plugin-payload-transport` shipped at commit `a10342f`. Operator pushed back on A3a's implicit `.gitignore:39` removal cost ("are we supposed to move dist to git?"), elected to run A1's 5-minute probe first. Probe commit `9f419aa` swapped `marketplace.json` from `ref: "release"` → `sha: "<release-HEAD>"`. V-3 attempt 3 install passed cleanly. After mid-probe latent M5 hooks-shape bug fix (commit `a18bca0`) + release-publish workflow re-run + sha bump (commit `2a7e145`), V-5 hook-fire smoketest passed (`reversibility-guard.sh` blocked the consumer's recursive-delete probe with the expected stderr). M7 closed at commit `3df4a53`. ADR superseded by `plugin-payload-transport-a1`. Real cost of the wrong reshape: one superseded ADR, one INV-012 wording revert, one schema-lint test rewrite, ~3-4 operator hours. Cost of running A1's probe first: 5 minutes plus the operator's instinct to say "wait, let's just try this."

**Anti-pattern signals**: "the adversarial argument is rigorous and the structural axis is correctly identified, so the heavier alternative is safer." "We have an empirical pattern in 82 plugins, but it might be stylistic — better to assume the conservative reading." "The structurally cleaner approach (A3a) is worth the operational cost because the cheap approach (A1) might fail." "Phase 3's verdict is RESHAPE; we should write the ADR with the new shape and probe afterward." "The operator's pushback on A3a's commit-dist cost is impatience; methodology says trust the adversarial verdict." Each signal is locally plausible. The pattern that catches them: when the candidate approach has a probe that costs less than 10 minutes and doesn't require infrastructure changes, **probe first, argue second**. The argument is preserved as part of the decision archaeology either way.

**Mechanism**: this lesson names the pattern; the corrective is at the convergence-note + Phase-3-mandate level (threshold rule + explicit "what cheap probe could falsify this attack?" line). Promotion to a `/decision` skill update (e.g., decision.full.md gains a "cheap-probe-cost-asymmetry" section) is deferred until a second instance confirms the pattern is generalizable beyond resolver-internals decisions. The interaction with `feedback_attack_before_synthesis.md` is constructive, not contradictory: attack-before-synthesis remains correct; this lesson adds a temporal qualifier — when the cheapest empirical probe is below the threshold, **probe before the attack locks in a verdict**.


## L-024: Single-feature schema drift is insufficient signal to amend a firm ADR — N≥3 trigger for WIDEN

**Discovered**: 2026-05-14, during the `feature-schema-d5-reconciliation` `/decision` arc triggered by Trial B T5 (`tests/unit/test_identifier_scheme_contract.py::test_d5_feature_files_well_formed`). The test surfaced that `.claude/features/orchestrator-paths.yaml` deviated from `identifier-scheme/D5`'s prescribed schema: used `charter:` instead of `intent:`, omitted `shaped-from:`, and added six fields not in D5 (`status`, `tracking`, `predecessor`, `lesson`, `audit-findings`, `out-of-scope`). Initial reflex was bimodal: NARROW (migrate the file) or WIDEN (amend D5). The /decision arc surfaced that single-instance drift cannot distinguish between "context-pressure drafting" and "genuine schema shortfall." 9/10 features conformed to D5; the outlier arose in a single Phase-2 commit (`df8ba20`) with no commit-message rationale.

**Pattern**: A feature file (or any artifact governed by a firm schema ADR) accumulates fields not enumerated in the schema. Operator reflex divides into NARROW (migrate to schema) vs WIDEN (amend the schema). Both are locally plausible; both close the immediate issue. WIDEN on N=1 sets a precedent — single-instance drift triggers ADR amendment — that future operators read as: "if I want a non-schema field, drift it in once and the schema follows." This inverts the firm-schema discipline: firm ADRs become advisory under pressure. Conversely, NARROW on N=1 with no record of why discards the kernel of legitimate need that may be re-discovered repeatedly.

**Load-bearing directive**: For any firm schema ADR, before invoking WIDEN via supersession on the basis of drift in feature/slice/ADR/handoff/feature-file artifacts, require **N≥3 independent instances** that each (a) need the same non-schema field(s), AND (b) cannot satisfy the need via an adjacent artifact (slice metadata, lessons.md, plan doc, ADR note). Concretely:

- **First non-conforming instance (N=1)**: migrate the artifact to the schema (NARROW). Record a watching-mark in `docs/lessons.md` enumerating the candidate non-schema fields and the artifact name. The fields may be retained as advisory (per the artifact-specific default-permit reading, if the schema permits) or relocated to a canonical home before deletion.
- **Second non-conforming instance (N=2) using same fields**: file a new `/decision` to re-evaluate, but presumption remains NARROW. Update the watching-mark to count = 2.
- **Third non-conforming instance (N=3)**: WIDEN via supersession is the default position; `/decision` evaluates whether to adopt.
- **"Independent" means different author contexts and different slice arcs.** Two slices in the same arc co-using a vocabulary do not count as N=2 — that is correlation within a single drafting context, not pattern.
- **"Need" means the field carries data with no canonical alternative home**, not that an author found it convenient. Convenience is not evidence of schema gap.

The N=3 threshold mirrors cairn's recurrence-promotion convention (L-011 uses 3 for mechanical-fix promotion). The threshold is a starting heuristic; ADR `schema-amendment-threshold` records it as firm/provisional and revisable on first counter-evidence.

**Rationale (≤100w)**: Cairn's firm/provisional distinction depends on firm decisions resisting amendment under single-instance pressure. WIDEN on N=1 erodes the distinction by demonstrating that drift triggers ratification; the methodology claim "firm ADRs are firm until ceremony" collapses if ceremony follows drift. The N≥3 threshold imposes a falsifiability check: drift must be reproducible across independent contexts before it is interpreted as schema signal. The threshold does not block schema evolution — it routes evolution through evidence-gathering rather than first-occurrence ratification. Cost asymmetry: NARROW on N=1 costs one file edit + one watching-mark; WIDEN on N=1 costs an ADR supersession + downstream propagation + permanent loosening of the firm-ADR norm.

**Concrete instance**: 2026-05-14. `.claude/features/orchestrator-paths.yaml` (single Phase-2 commit `df8ba20`, no rationale) carried six non-D5 fields. Operator reflex invoked /decision on whether to NARROW or WIDEN. Phase 0 confirmed no code reads feature-file fields (`scripts/validate_architecture.py`, `cairn-tdd-feature/SKILL.md` both skip). Phase 1 surfaced six failure scenarios; risk asymmetry favored NARROW. Phase 2 enumerated three approaches (NARROW pure, NARROW+lesson [HYBRID], WIDEN-via-supersession). Phase 3 stress-tested HYBRID and confirmed it survives. Phase 5 independent verification reached WIDEN-supersede via a more permissive D5 reading (default-permit-with-named-rejection only; no required floor); operator chose to keep the NARROW+lesson framing and record the divergence here for archaeology. ADR `schema-amendment-threshold` records the protocol; this lesson records the pattern. Watching-mark filed: orchestrator-paths instance 1/3 for fields `tracking`, `predecessor`, `lesson`, `audit-findings`, `out-of-scope`, top-level `status`.

**Anti-pattern signals**: "this field is intuitively useful." "the author added it for good reasons." "most features will eventually need this." "migrating it away loses data." ## L-025: Cairn's governance infrastructure is orthogonal to its four-phase methodology — they are separable layers

**Discovered**: 2026-05-20, during the `identity-and-scope-deferral` `/decision` arc prompted by `docs/plans/2026-05-19-adaptive-reliability-direction.md`. Phase 0.5 user-journey trace surfaced the finding; Phase 3 disconfirming search verified it against the codebase.

**Pattern**: Cairn ships two architecturally separable layers:

1. **Governance infrastructure** — hooks (`checks/reversibility-guard.sh`, `checks/role_guard.py`, `checks/reality-check.sh`), validators (`scripts/validate_architecture.py`), append-only ADR contract (enforced by reversibility-guard), handoff-pointer contract (`tests/unit/test_handoff_contract.py`), identifier scheme (`docs/adr/identifier-scheme.md`), role guards via operator envelope (`.claude/active-envelope.yaml`), plan-doc shape (frontmatter `id:` + `envelope:`).

2. **Four-phase TDD methodology** — `cairn-tdd-feature` dispatch skill (`.claude/skills/cairn-tdd-feature/SKILL.md`), phase agents (`.claude/agents/phase-{1..4}-tdd.md`), per-phase commit gates, `RAISE_ISSUE` flow.

The methodology consumes the infrastructure (role_guard reads `AGENT_ROLE` when dispatch context is set), but the infrastructure does NOT depend on the methodology being invoked. Verified:

- `checks/role_guard.py:43-45,137-167` — when `AGENT_ROLE` is unset, the hook falls through to operator-envelope enforcement. The dispatch path is one mode; the envelope path is the other. Both are first-class.
- `scripts/validate_architecture.py:443-445` — phase names appear only in role-to-path mapping, not in any required-pipeline state read. No `.claude/skill-runs/` path is required for validation.
- `tests/unit/test_handoff_contract.py` — handoff contract validates pointer resolution; pointers may target GitHub issues, ADRs, plan docs, or commits, regardless of whether the work flowed through dispatch.

**Implication for identity-level reasoning**: the four-phase methodology is one named consumer of the governance infrastructure; ad-hoc edits under operator envelope and `/decision`-arc work are co-equal consumers. None is "Cairn's identity" in a way that the others are not.

**Implication for proposal scrutiny**: design proposals that frame Cairn's identity at the methodology layer (e.g., "Cairn is the four-phase methodology") are foundational claims, not structural readings — the structure of the repo does not entail them. Proposals that frame Cairn's identity at the infrastructure layer (e.g., "Cairn is governance infrastructure; methodology is a preset") are likewise foundational, not structural. The orthogonality is a structural fact; what to identify Cairn AS is a strategic claim downstream of it. Conflating the two (`I've discovered the structure, so the strategic claim follows`) is the named failure mode.

**Concrete non-application**: this lesson does NOT entail that the four-phase methodology should be deprioritized or that the infrastructure should be promoted to the product's headline identity. ADR `identity-and-scope-deferral` (2026-05-20) explicitly defers that strategic choice on the grounds that external evidence has not accumulated. The lesson is a structural fact; the deferral is the strategic position taken.

**Anti-pattern signals**: "the orthogonality means the methodology is just one preset, so we should reframe Cairn as infrastructure" — structural fact mistaken for strategic conclusion. "The bypass paths are equivalent to the methodology" — structural separability conflated with substitutability; the four-phase path is the highest-evidence path even though all three paths consume the same infrastructure. "Since the infrastructure survives without the methodology, the methodology is vestigial" — separability does not imply atrophy; the methodology is the right tool for the kind of work it was built for (high-consequence multi-phase invariant work). Right-sizing is not rot.

**Mechanism**: this lesson is the canonical record. ADRs proposing identity-level framing changes should engage with the orthogonality as a structural input but not as a sufficient condition. The decision arc artifacts at `.claude/skill-runs/identity-and-scope-2026-05-20/outputs/` contain the full pre-mortem and stress-test evidence. Cross-reference: `[[identity-and-scope-deferral]]`, `[[adr-contract-execution-scope-clause]]`.

## L-026: When /decision's choice axis is operator-priority-bound, the right Phase 4 output is default-with-explicit-pivot, not a clean pick

**Discovered**: 2026-05-20, during the `interaction-protocol-next-phase` `/decision` arc (`.claude/skill-runs/interaction-protocol-next-phase-2026-05-20/`). Phase 3 stress-tested four approaches (RETROFIT, TRIAL-C, TIGHTEN-FIRST, FREEZE+DISTRIBUTE) and eliminated two (TIGHTEN-FIRST self-eliminated under contestation of its motivating premise; RETROFIT eliminated as primary on no-protocol-learning grounds). The two survivors answered *different questions* — TRIAL-C answered "what's the next trial that pressure-tests the contract pattern?"; FREEZE+DISTRIBUTE answered "is more in-repo trial-iteration still the highest-value activity?". The choice between them turned on an operator-priority axis ("learning velocity per session" vs "calendar pressure + external signal as next-needed evidence class") that was BELIEVED-not-VERIFIED in Phase 1's load-bearing-claim audit.

**Pattern**: When Phase 3 stress test leaves two viable approaches whose ranking depends on an operator-priority axis (rather than evidence the /decision protocol can itself discover), there is no "clean pick" available without forcing the operator to choose. The default-with-pivot pattern preserves momentum (the ADR commits to the default) while keeping supersession cheap (the alternative is recorded as the active alternative, not as a rejected option). Forcing a clean pick by collapsing the axis to a single dimension (e.g., "calendar pressure always wins" or "learning velocity always wins") falsifies the operator's actual decision surface; deferring entirely to ask leaves the decision homeless.

**Load-bearing directive**: For any `/decision` whose Phase 3 synthesis identifies an unresolved operator-priority axis between two surviving approaches, the Phase 4 ADR MUST:

1. **Record the chosen default with full architectural commitments** — the ADR is fully actionable as written; no "pending operator input" placeholders in `## Decision`.
2. **Record the alternative in `## Alternatives Considered` as the *active* alternative** — explicitly distinguished from eliminated alternatives. The phrasing convention: "**Recorded as the active alternative**, not eliminated. The motivating claim — [X] — is BELIEVED, not VERIFIED. If operator priority signal shifts to [Y], this ADR is the right candidate for supersession."
3. **Make the supersession path explicit and cheap** — provisional firmness, named supersession trigger, preserve any deadline-pressured carve-outs from the active alternative inside the default (e.g., this ADR's D6 Node-20 carve-out preserves FREEZE+DISTRIBUTE's most calendar-pressured piece).
4. **Risk-register the priority shift** — list "operator priority shifts mid-arc to [active alternative]" as a documented risk with the supersession path as the handling.

The pattern is NOT applicable when the choice axis is evidence-discoverable (e.g., a /decision waiting on a probe per L-023). It IS applicable when the axis is operator-bound and no further probe will produce signal (e.g., learning-velocity-vs-distribution where both branches are real activities, not propositions to be tested).

**Rationale (≤100w)**: Phase 3's job is to surface meta-questions, not pre-empt them. When the operator-priority axis is BELIEVED-not-VERIFIED, picking blindly forces a position the operator never authorized; deferring entirely makes the /decision a question, not a decision. Default-with-pivot threads the needle: the ADR is actionable (preserves momentum); the alternative is recorded with cheap supersession (preserves option value). The pattern mirrors `[[identity-and-scope-deferral]]`'s deferral-with-recorded-pivot but applies it to choice between two viable activities, not to deferring a single activity. The framing is also consistent with cairn's provisional/firm distinction: provisional decisions are expected to be revisited.

**Concrete instance**: 2026-05-20. The `interaction-protocol-next-phase` arc Phase 3 synthesis (`.claude/skill-runs/interaction-protocol-next-phase-2026-05-20/05-stress-test-and-synthesis.md`) recommended TRIAL-C as default with two carve-outs: (a) #32 Node-20 bump executed inline before TRIAL-C session 1 (preserves FREEZE+DISTRIBUTE's calendar-pressured piece); (b) FREEZE+DISTRIBUTE recorded as the active alternative so the pivot is cheap. ADR `[[slice-intent-contract]]` commits TRIAL-C as actionable Decision; `## Alternatives Considered` Alternative C records FREEZE+DISTRIBUTE per the active-alternative phrasing convention; Risk Register R4 names the priority shift with provisional firmness as the handling. The /decision lands actionable without forcing a priority claim the operator hasn't made.

**Anti-pattern signals**: "Phase 3 found two viable approaches; we should write two ADRs and let the operator pick." (Splits the decision into the operator's lap with no default — abandons the /decision's job.) "Phase 3 verdict is TRIAL-C; the FREEZE+DISTRIBUTE attack is interesting but ultimately superseded by the synthesis recommendation." (Collapses the active alternative into a rejected one; loses the cheap-pivot property.) "The operator said 'do C'; that resolves the priority axis." (Conflates a goal-setting instruction with a priority-axis claim — "do C" means "do step C of the goal", not "my priority is X over Y".) "We need to ask before writing the ADR." (Conflates writing an actionable ADR with locking the decision; provisional firmness + active-alternative recording is what makes the ADR cheap to flip.)

**Mechanism**: this lesson names the pattern; the corrective is at the `/decision` Phase 4 mandate level (decision.full.md's ADR section gains an "active-alternative phrasing convention" sub-rule). Promotion to a `/decision` skill update is deferred until a second instance confirms the pattern is operationally recurrent (per L-024 N≥3 threshold for skill amendments). Watching-mark: `interaction-protocol-next-phase` 2026-05-20 instance 1/3. Cross-reference: `[[slice-intent-contract]]`, `[[adr-contract-execution-scope-clause]]` (the carve-out preserved inside the default uses execution-scope grammar), `[[identity-and-scope-deferral]]` (sibling pattern of recorded-pivot at the strategic layer).

## L-027: Adversarial analysis can rationalize the null action — a /decision that attacks every commitment until deferral wins is paralysis dressed as rigor

**Pattern**: In a `/decision` Phase 3 (adversarial stress-test), attacking every load-bearing claim hard enough makes the *null action* — defer the change, supersede the minimum, demote the motivating idea to an inert sub-claim — win by default, because every concrete commitment carries risk and every proposed mechanism is "unbuilt." The synthesis then dresses inaction as prudence ("low blast radius," "convergence"). This is the inverse failure of `feedback_attack_before_synthesis`: attack-before-synthesis is correct; attack-*into-paralysis* is not. "Convergence on deferral" across independent inputs is usually shared risk-aversion, not consensus on a positive answer.

**Corrective**: After the adversarial pass, do not let attack-completeness select for inaction. Find the one mechanism that *both* survives the attacks *and* is buildable now, and commit to it — then prove buildability by building a spike, not by asserting it. Distinguish convergence on a positive commitment (real correlated-error defense) from convergence on deferral (suspect). Recognition cue: a synthesis that supersedes the smallest possible set + defers all mechanisms + demotes the motivating idea to a do-nothing sub-claim, and calls it "low blast radius," is probably the null action wearing prudence's clothes.

**Concrete instance**: 2026-05-30, cairn identity arc. The first synthesis (`.claude/skill-runs/cairn-identity-decision-2026-05-30/06-synthesis.md`) deferred the methodology change, the re-injection hook, and the firm-ADR supersession, and demoted "goal-commitment vs reactivity" to an inert sub-claim — net change ≈ status flips. The operator flagged it a "cop-out." Re-synthesis recognized that **premise-grounding** — already present but buried as D2.5 of the merged `[[cairn-thin-substrate-direction]]` ADR — was the keystone: it catches the one failure nothing else does (the slice-#25 wrong-premise), mechanizes the deferred intent↔ADR alignment by diffing a *verbatim quote* instead of *semantics*, and is buildable now as a ~40-LOC sibling of an existing validator assertion. Built and shipped the same session (`scripts/validate_architecture.py` `premise-grounding` type + `tests/unit/test_premise_grounding.py`); identity reframed to evidence-grounding (ADR D7).

**Anti-pattern signals**: "Every approach has a fatal flaw, so the safest move is to defer." "All the inputs agree we should wait — strong convergence." "The mechanism is unbuilt, so the decision can't commit to it." (Buildability is testable — build a spike.) "Low blast radius" praising a recommendation that changes nothing.

**Mechanism / cross-refs**: corrective belongs at `/decision` Phase 3→4 — a synthesis must name the positive commitment that survives the attacks, and prove a load-bearing mechanism is buildable, before recommending deferral. Cross-references: `[[cairn-thin-substrate-direction]]` (D7, the keystone this arc shipped), L-023 (cheap empirical probes trump strong adversarial argument — here a cheap *build* trumped argument), L-025 (infrastructure⊥methodology — the decoupling that let the firm phase ADRs be retained, not superseded), operator memory `feedback_attack_before_synthesis` (this lesson is its guardrail). Watching-mark: instance 1/3.

## L-028: A compressed human-approval object bounds the ceiling (scope), never the floor (severity) — declare the floor or intent silently erodes within scope

**Pattern**: When an agent drafts a formal artifact (EARS contract, spec, test plan) under a compressed human-approved anchor — a one-line "promise", a sign-off card, a charter — the anchor constrains *scope from above* ("nothing exceeds the promise") but is silent on the *floor from below*: the severity, polarity, and must-fail semantics *within* scope. A clause can honor the promise's scope and still under-deliver the actual intent, and no party ever signed an object that pins the floor. Every grounding/atomicity gate passes (they read scope and structure, not floor), and the wrong-intent ships green. This is the slice-#25 wrong-premise failure relocated one abstraction level up — from the premise→source gap to the anchor→clause gap.

**Corrective**: Do not trust the compressed anchor to carry load-bearing semantics it cannot express. Apply the premise-grounding posture one level up: (1) **mechanize the structural edge** — a deterministic anchor↔clause traceability check (orphan clause = smuggled scope; unrealized anchor line = dropped behavior); (2) **declare the floor** — a *mandatory* per-clause severity field (`mandatory|advisory`) so silent floor-erosion becomes a visible, objectable line; (3) **attack the semantics** with a fresh-context fidelity challenger (is each edge honest / under-realized?); (4) **record the honest limit EXPOSED** — same-family review ~60% co-misses; it raises the floor, it does not close the hole. Never narrate the structural check as if it caught semantics.

**Concrete instance**: 2026-05-31, `[[intent-contract-cost-model]]` /decision. The operator's "promise model" (user approves a plain-language promise; agent owns the formal proof) was adversarially stress-tested: the m5 A10 "fail-loud / declare-unsafe" canary could be drafted as "the validator shall report a result" — grounded ✓, atomic ✓, within-promise ✓ — and ship as log-and-exit-0, its reason silently gone. The cost-model ADR commits only the invariant (user approves the promise; agent owns the proof) + cost-removal; the floor mechanisms — mechanize the edge (traceability), declare the floor (severity as the *challenger's* input, never user review), attack the semantics (a fidelity challenger) — are recorded there as **deferred design constraints** for a measured heavy-band follow-on, **not accepted for implementation**. Prior instance of the same posture: `[[cairn-thin-substrate-direction]]` D7 premise-grounding (mechanize the *verbatim quote* edge; accept it can't catch a misread).

**Anti-pattern signals**: "The user approved the promise, so anything consistent with it is fine." "Nothing exceeds the promise" stated as a *sufficient* invariant. A sign-off / promise / charter treated as the floor when it only sets the ceiling. Shipping an agent-drafted formal layer under a human anchor with no severity field and no fidelity attacker. Narrating a cardinality/coverage check as if it verified meaning.

**Mechanism / cross-refs**: corrective belongs wherever an agent formalizes under a compressed human anchor. Cross-references: `[[intent-contract-cost-model]]` (D3 + "Deferred design constraints" — the candidate mechanism, deferred to a measured heavy-band follow-on, **not** accepted for implementation), `[[cairn-thin-substrate-direction]]` (D7, the prior premise-grounding instance of mechanize-edge / declare-floor / accept-limit), `[[intent-management-loop]]` (D2/D4, the front-challenge slot a future fidelity attacker would widen and the ~60% same-family residual it inherits). Watching-mark: instance 1/3 (premise-grounding is the sibling at the grounding layer; this is the severity/floor layer).
