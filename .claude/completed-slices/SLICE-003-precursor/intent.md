# Intent — SLICE-003-precursor: ADR-004 D4 surfacing

## What and Why

This slice operationalizes ADR-004's D2 (named roles), D3 (`adrs-referenced` immutability gate), and D4 (Phase Skill Guide registry + phase-entry surfacing) by landing the three textual mechanisms ADR-004 committed to as pre-D1 follow-through.

The precursor is the mitigation for ADR-004 Risk F6 ("roles named textually but become dead text that nothing surfaces"). ADR-004 Consequences (`docs/adr/004-phase-lock-and-role-declaration.md:186`) names this follow-up explicitly and warns that if it does not land within two slices of ADR-004, **F6 is materially unmitigated and ADR-004 is on a trajectory to supersession**. This slice is that follow-through.

It is explicitly **pre-D1**: it does not fold into SLICE-003 (the D1 design slice in `docs/plans/2026-04-11-adr-003-v1-execution-plan.md` §Tier 1). SLICE-003 depends on this precursor landing so its own Phase 1 Reader session inherits a live role/skill surfacing mechanism rather than dead ADR text.

INV-003 (from `docs/ARCHITECTURE.md:16`) already asserts that phase-entry surfacing happens via `docs/operational-reference.md § Phase Skill Guide`. That section does not yet exist. This slice makes the invariant true.

## Specification Detail

### S1 — `docs/operational-reference.md § Phase Skill Guide` exists as a new section

The section heading is exactly `## Phase Skill Guide`. The section body:

- **S1.a** Carries the D4 mapping table from `docs/adr/004-phase-lock-and-role-declaration.md:72-76` with columns: Phase, Role, Primary skills, Supporting skills, Notes on adaptation. Table content is lifted from ADR-004 verbatim for initial landing; subsequent updates are ordinary documentation edits and do not require ADR supersession.
- **S1.b** Carries the explicit-exclusions list from ADR-004 lines 78–84 (why `dispatching-parallel-agents`, `executing-plans`, `finishing-a-development-branch`, `using-git-worktrees`, `writing-skills`, and `writing-plans` are NOT in the primary mapping).
- **S1.c** States at the top that the section is a **living registry** — analogous to how `docs/ARCHITECTURE.md` is regenerated by `/refresh-architecture`, updates to skill names do NOT require ADR supersession.
- **S1.d** Cites ADR-004 as authoritative source for the phase count, phase names, role names, and the constraint that changes to those require a superseding ADR.

### S2 — `/catchup` surfaces role, anti-behaviors, and skills at phase entry

`commands/claude-code/catchup.md` Mode A (Pipeline Phase) phase-load sub-sections (Phase 1, 2, 3, 4) MUST instruct the agent to read the Phase Skill Guide and print the target phase's:

- Role name (Reader / Skeptic / Builder / Auditor)
- Primary anti-behavior and secondary anti-behaviors (from `docs/adr/004-phase-lock-and-role-declaration.md:50-55` D2 table)
- Primary skills and supporting skills (from Phase Skill Guide S1.a)

Surfacing happens **at phase entry**, alongside the existing "Loaded:" / "Excluded:" / "Gate:" report. Exact format is Builder's call; only the required content fields are specified here.

### S3 — `/start-slice` surfaces role, anti-behaviors, and skills at phase entry

`commands/claude-code/start-slice.md` MUST instruct the same surfacing as S2, at the moment the skill transitions into a target phase. Concretely: after Step 3 (Phase Gate Validation) passes and before the phase-specific guidance (Phase 2 / Phase 3 / Phase 4 sub-sections), print the target phase's role, anti-behaviors, and skills. Exact format is Builder's call.

### S4 — D3 `adrs-referenced` structural-immutability gate in `/start-slice` Step 3

`commands/claude-code/start-slice.md` Step 3 gate table gains one additional rule on the Phase 2 row: advancing from Phase 1 (Intent) to Phase 2 (Validation) requires that every ADR named in `intent.md`'s `adrs-referenced` YAML field exists as a committed file in `docs/adr/`.

- **S4.a** Verification command: `git log --oneline -- docs/adr/<adr-slug>.md` returns ≥1 commit for each declared ADR.
- **S4.b** Empty `adrs-referenced` field passes the gate trivially — this matches low-consequence-slice semantics and does not add friction to cleanup or pure-implementation slices, per `docs/adr/004-phase-lock-and-role-declaration.md:61`.
- **S4.c** Failure message, when the gate blocks, MUST name the missing ADR slug(s) and MUST NOT silently pass.

### S5 — Surfacing and gate are instructed, not hook-enforced

No new `checks/*.sh` hook is introduced. No new Python validator check. The three mechanisms (S1, S2+S3, S4) live entirely in textual protocol within the three envelope files. This is the direct consequence of ADR-004 D2's "Roles are instructed, not hook-enforced" and ADR-003 D4's v1 time-box on mechanization.

### S6 — INV-003 realization

After this slice lands, `docs/ARCHITECTURE.md:16` INV-003's claim that "each phase's role and anti-behaviors are surfaced at phase entry by `/catchup` and `/start-slice` via `docs/operational-reference.md § Phase Skill Guide`" resolves to a true statement — the section it references exists, and the skills it names instruct the surfacing.
