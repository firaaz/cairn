## Findings

### Finding #1 — `test_d3_bypass_log_format.py` (2 failures) — STALE ROOT-FIX POINTER

**Test failures:**
- `test_every_line_matches_classified_regex` — lines 8–10 of `.claude/d3-bypasses.log` do not match the regex because the regex still requires `^SLICE-\d+ ` (legacy shape) while the migration to hierarchical slice IDs produced entries like `identifier-scheme/slice-and-feature-rename 2026-04-18 ...`.
- `test_line_order_is_chronological` — same regex parses the slice-id suffix as `int(id_.split("-")[1])`, which raises `ValueError` on hierarchical form.

**Why the cited fix did not land:** `d3-bypasses.log:11` cites `v1-defense-d3/bypass-log-test-resilience` as the root-fix owner. That slice closed **2026-04-17** at commit `7b5ed12`; its Phase 3 implementation (`6664c94`) only widened the regex's *qualifier* group (`(?: \([A-D]\))?`) — it did not widen the `SLICE-\d+` prefix. The hierarchical-ID migration entries were appended to the log on **2026-04-18**, after that slice had closed. The handoff pointer and the in-log citation are both **stale**.

**Schema-violation sub-finding:** Line 8 uses `operator Option C:` as the class token. The three-class schema is `{slice-caused | pre-existing | false-positive}`. `operator` is not valid. This is an additional violation beyond the slice-ID shape; a regex widening alone will not make this line compliant. Introduced by commit `41c4c57` (`slice: identifier-scheme/slice-and-feature-rename — complete`).

**Recommendation:** open a new slice — candidate id `v1-defense-d3/bypass-log-hierarchical-slug` — that (a) widens the slice-id token in `CLASSIFIED_LINE_RE` to match both `SLICE-\d+` and `[a-z][a-z0-9-]*/[a-z][a-z0-9-]*`, (b) widens the `_ids()` chronology helper to stop parsing `int(suffix)` for hierarchical form, (c) adds a legality check or migration for line 8's `operator Option C:` class token. Could also be absorbed into compression Slice A if that slice's envelope already touches substrate tests.

**Verdict:** FAIL gate, but failure is pre-existing and correctly logged; no slice-in-window caused it. Fix belongs in a successor slice, not by retroactive edit (rule 9).
